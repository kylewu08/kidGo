# 親子出遊決策工具 — 設計架構書 v0.2

> 專案代號：**KidGo**（暫定） 文件目的：作為 Claude Code 的實作依據，定義產品邊界、資料模型、核心邏輯與開發階段。 最後更新：2026-08  
>   
> **v0.2 更新重點**：釐清「不是資料庫」的真正含義；新增決策三來源模型；明確定義 AI 在架構中的位置與禁區；新增 AI 輔助建檔流程。

---

## 0\. 一句話定義

**這不是一個以「收錄完整」為目標的景點資料庫，而是一個「這個週末帶小孩去哪」的決策引擎。**

給定「今天的天氣 × 小孩目前的作息階段 × 可接受的車程 × 現在幾點」，直接回答一到三個具體答案，而不是列出五十個選項讓使用者自己篩。

> **措辭澄清**：本產品當然有資料庫。「不是資料庫」指的是**野心的邊界**——價值來自判斷的準確度，不是收錄的完整度。收錄數量永遠不是 KPI。

## 1\. 設計原則（所有實作決策以此為準）

| \# | 原則 | 實務意涵 |
| :---- | :---- | :---- |
| P1 | **個人優先，非平台** | 第一個使用者是開發者自己。不做 UGC、不做社群、不做評論系統。沒有冷啟動問題。 |
| P2 | **答案優先，非清單** | 預設畫面是「今天建議去 X」，不是搜尋框。清單是次要視圖。 |
| P3 | **窄而深，非廣而淺** | v1 只收錄開發者實際會去的 40–60 個地點。 |
| P4 | **紀錄是長期資產** | 每次出遊後的實際紀錄，是任何現有平台無法複製的資料。但它是**慢變數**，不是第一天的價值來源（見 §2）。 |
| P5 | **誠實不可交易** | 推薦排序永不接受付費影響。變現只能發生在「使用者已決定要去之後」。 |
| P6 | **離線可用** | 出門在外網路可能不穩。核心資料本地優先。 |
| P7 | **決策邏輯必須可讀可測** | 評分規則是本產品最有價值的資產，必須以程式碼形式存在，不得externalise 給黑箱模型（見 §3）。 |

## 2\. 決策的三個來源（本產品的核心心智模型）

推薦結果不是靠單一資料源產生，而是三層疊加。**它們抵達的時間點不同，這決定了產品第一天就能用。**

| 層 | 來源 | 何時具備 | 在評分中的角色 | 佔比 |
| :---- | :---- | :---- | :---- | :---- |
| **L1 判斷力** | 開發者腦中既有的育兒常識 | **第一天** | 硬性過濾（Stage 1） | 決定「哪些不可能」 |
| **L2 靜態事實** | 地點建檔資料（可由 AI 輔助） | 建檔完成後 | 加權評分主體（Stage 2） | 決定「哪些可能」 |
| **L3 實際紀錄** | `Visit` 累積 | 持續累積 | 評分微調 | 決定「哪些真的行」，僅佔 **5%** |

### L1 範例（這些直接寫成 Stage 1 過濾條件）

- 降雨機率 \> 60% → 純戶外剔除  
- 午睡起點前無法返家 → 剔除  
- 使用推車但地點不友善 → 剔除  
- 車程超過上限 → 剔除

這一層做完，50 個地點通常只剩 5–10 個。**這在零紀錄狀態下就能完成，是產品第一天可用的原因。**

### L3 的正確定位

歷史成效權重刻意只給 5%。理由：三筆紀錄算不出可信平均值，過度加權只會產生雜訊。

**紀錄真正的價值不在於自動調整排序，而在於讓開發者發現自己填錯了靜態欄位。** 例如：

某公園  energyBurn: 4, typicalDurationMin: 120  ← 建檔時的猜測

18m  09:30-10:45  outcome 2  meltdown ✓

20m  09:00-10:30  outcome 3  meltdown ✓

23m  09:15-11:20  outcome 5  meltdown ✗

→ 結論不是「這地點不好」，而是「兩歲前撐不到兩小時」→ 手動把 `sweetSpotAge.minMonths` 改成 22。

因此 UI 必須提供\*\*「地點的歷史紀錄摘要」\*\*視圖，讓這種模式肉眼可見。這比任何自動化的權重學習都重要。

## 3\. AI 在架構中的位置

┌─────────────────────────────────────────┐

│  資料層   ✅ 使用 AI                      │

│  建檔、抽取結構化欄位、補齊資訊            │

└─────────────────────────────────────────┘

                   ↓

┌─────────────────────────────────────────┐

│  決策層   ❌ 不使用 AI                    │

│  確定性評分函式，可測試、可調參、可除錯    │

└─────────────────────────────────────────┘

                   ↓

┌─────────────────────────────────────────┐

│  呈現層   ✅ 使用 AI                      │

│  將分數翻譯成人話、對話式條件調整          │

└─────────────────────────────────────────┘

### 3.1 為什麼決策層禁用 AI

| 問題 | 後果 |
| :---- | :---- |
| 不可重現 | 同樣條件不同答案，無法回答「為什麼今天變了」，也就無法調參 |
| 幻覺代價不對稱 | 「推車可進、四點才關門」答錯一次＝帶小孩白跑一趟。不是重跑一次能補救的錯誤 |
| 紀錄無法回饋 | `Visit` 資料需要一個可修改的評分函式才能發揮作用，丟進 prompt 是黑箱 |
| 成本 | 純函式零成本，每次查詢呼叫模型則否 |

### 3.2 護城河檢查（重要）

若本產品僅是「AI 搜尋並推薦」，使用者今天即可用 ChatGPT 免費達成，產品無存在必要。

**聊天介面給不了的三件事，必須是本產品的核心：**

1. **持久狀態** — 不需每次重述小孩月齡、作息、車程上限；且這些條件隨月齡自動演進  
2. **驗證過的在地事實** — 親自確認的停車狀況、實際車程，非模型推測  
3. **個人歷史** — 「上次 18 個月來撐了兩小時」，任何模型都生不出來

實作上這意味著：**`Child`、`Place`、`Visit` 三張表的持久化，比推薦演算法本身更接近產品的本質。**

## 4\. 範圍界定

### v1 要做

- 地點資料的建檔與編輯（含 AI 輔助建檔，見 §7）  
- 天氣整合（中央氣象署開放資料）  
- 「今天去哪」推薦引擎  
- 出遊紀錄（check-in / 事後回填）  
- 地點歷史摘要視圖（支援 §2 的欄位修正流程）  
- 多個小孩的年齡與作息階段管理

### v1 明確不做

- 使用者註冊、多租戶、權限系統  
- 社群、評論、按讚、分享  
- 業者上架後台  
- 全台景點爬蟲與大量匯入  
- 行程規劃（多點串接、逐小時排程）— v2 以後  
- 任何形式的廣告  
- **以 LLM 直接產生推薦排序**

>   
> **反模式警告**：一旦開始追求「收錄全台景點」，這個專案就死了。資料維護成本會吃掉所有開發時間。AI 輔助建檔是用來**降低 50 筆的成本**，不是用來**擴張到 5000 筆**。

## 5\. 資料模型

### 5.1 Child（小孩）

interface Child {

  id: string;

  name: string;

  birthDate: string;          // ISO date

  napStage: NapStage;         // 可由月齡推算，允許手動覆寫

  wakeTime: string;           // "07:00"

  napWindows: TimeWindow\[\];   // \[{ start: "12:30", end: "14:30" }\]

  bedTime: string;            // "20:30"

  mobility: Mobility;

  notes?: string;

}

type NapStage \=

  | "two\_naps"      // 約 6-14m

  | "one\_nap"       // 約 14-36m

  | "transitioning" // 2→1 或 1→0 過渡期

  | "no\_nap";       // 約 3y+

type Mobility \=

  | "carried"       // 需揹/抱

  | "stroller"      // 主要靠推車

  | "walks\_short"   // 能走但續航短

  | "walks\_full";

**設計理由**：`napStage` 與 `mobility` 是推薦邏輯的支點，也是本產品相對於一般旅遊 App 的結構性優勢——它們每 3–6 個月改變一次，推薦結果必須跟著變，這本身構成回訪理由。

### 5.2 Place（地點）

**欄位設計原則：只記錄 Google Maps 和現有懶人包查不到的東西。**

interface Place {

  id: string;

  name: string;

  category: Category;

  // \--- 位置 \---

  lat: number;

  lng: number;

  address: string;

  driveMinutes: number;       // 從家出發的實際車程（手填，非 API 估算）

  parking: ParkingRating;

  // \--- 核心：現有平台查不到的欄位 \---

  energyBurn: 1|2|3|4|5;            // 放電強度

  typicalDurationMin: number;        // 實際能撐多久（非官方建議時間）

  bestTimeSlots: TimeSlot\[\];

  ageRange: { minMonths: number; maxMonths: number };

  sweetSpotAge?: { minMonths: number; maxMonths: number };

  // \--- 環境條件 \---

  indoor: IndoorType;

  shadeLevel: 0|1|2|3;

  strollerFriendly: boolean;

  hasChangingTable: boolean;

  hasNursingSpace: boolean;

  hasFoodOnSite: boolean;

  hasWaterPlay: boolean;

  needsReservation: boolean;

  // \--- 實務情報 \---

  quietHours?: string;

  crowdLevel: { weekday: 1|2|3|4|5; weekend: 1|2|3|4|5 };

  costPerFamily?: number;

  indoorBackupPlaceIds?: string\[\];

  // \--- 主觀 \---

  personalRating?: 1|2|3|4|5;

  notes?: string;

  tags: string\[\];

  // \--- 資料來源追蹤（v0.2 新增）---

  fieldSources: Record\<string, FieldSource\>;  // 每個欄位的來源

  lastVerifiedAt?: string;

}

type FieldSource \= "manual" | "ai\_suggested" | "ai\_confirmed" | "visit\_corrected";

type Category \=

  | "park" | "playground" | "indoor\_playground" | "museum"

  | "farm" | "beach" | "trail" | "kids\_cafe" | "mall" | "library" | "other";

type IndoorType \= "indoor" | "outdoor" | "mixed" | "covered\_outdoor";

type TimeSlot \= "early\_morning" | "morning" | "post\_nap" | "late\_afternoon";

type ParkingRating \= "easy" | "moderate" | "hard" | "none";

**`fieldSources` 的必要性（v0.2 新增）**：AI 建議的欄位可信度低於親身驗證的欄位。UI 上必須能區分「AI 猜的」與「我確認過的」，否則錯誤資料會混入而無法追查。這是使用 AI 輔助建檔的必要配套。

### 5.3 Visit（出遊紀錄）

interface Visit {

  id: string;

  placeId: string;

  childIds: string\[\];

  date: string;

  arrivedAt: string;

  leftAt: string;

  childAgesMonths: number\[\];  // 快照，不要用 birthDate 反推

  weatherSnapshot: {

    condition: string;

    tempC: number;

    rainProbability: number;

  };

  outcome: 1|2|3|4|5;

  actualEnergyBurn: 1|2|3|4|5;

  napHappened: boolean;

  meltdown: boolean;

  wouldReturn: boolean;

  notes?: string;

  photos?: string\[\];

}

**為什麼記 `childAgesMonths` 快照**：兩年後回頭看「小孩 18 個月時的結果」才有意義，用出生日期反推會失去當下情境。

**為什麼記 `meltdown`**：最誠實的訊號。長期累積能反推出「這地點對這年齡不適合」，是懶人包永遠給不了的洞察。

### 5.4 HomeBase

interface HomeBase {

  lat: number;

  lng: number;

  cwaLocationName: string;    // 對應中央氣象署鄉鎮預報地區名，如「板橋區」

  maxDriveMinutes: number;

}

## 6\. 核心推薦引擎

### 6.1 輸入

interface RecommendContext {

  timestamp: Date;

  children: Child\[\];

  weather: WeatherForecast;

  maxDriveMinutes: number;

  availableWindow: TimeWindow;

  excludeRecentDays?: number;    // 預設 14

}

### 6.2 Stage 1 — 硬性過濾（來自 L1 判斷力）

不符合直接剔除，不進入評分：

\- driveMinutes \> maxDriveMinutes                            → 剔除

\- 可用時間 \< (driveMinutes × 2 \+ typicalDurationMin × 0.6)  → 剔除

\- 降雨機率 \> 60% 且 indoor \=== "outdoor"                     → 剔除

\- 體感溫度 \> 33°C 且 indoor \=== "outdoor" 且 shadeLevel \<= 1 → 剔除

\- 小孩月齡不在 ageRange 內                                    → 剔除

\- mobility \=== "stroller" 且 \!strollerFriendly               → 剔除

\- needsReservation 且 為當日決策                              → 標記警示（不剔除）

> 這些門檻值應集中在 `lib/recommend/thresholds.ts`，方便日後依實際經驗調整。

### 6.3 Stage 2 — 加權評分（0–100）

| 因子 | 權重 | 計算方式 |
| :---- | :---- | :---- |
| 作息契合度 | 30% | 現在時段是否落在 `bestTimeSlots`；能否在午睡前完成或午睡後開始 |
| 年齡契合度 | 25% | 落在 `sweetSpotAge` 滿分，僅落在 `ageRange` 給部分分 |
| 天氣適配度 | 20% | 晴天戶外加分；`shadeLevel` 對高溫的補償 |
| 新鮮度 | 10% | 距上次造訪越久越高；`excludeRecentDays` 內大幅降權 |
| 車程成本 | 10% | 非線性，30 分鐘內差異不大，超過後急降 |
| 歷史成效 | **5%** | `Visit.outcome` 平均；`meltdown` 為負向 |

> **歷史成效權重刻意壓低至 5%**，理由見 §2。此值不應在紀錄筆數少於 20 筆前調高。  
>   
> **多小孩情境**：對每個小孩獨立算分，取**最低分**而非平均。理由：只要有一個不適合，整趟就毀了。這是刻意的保守設計。

### 6.4 Stage 3 — 多樣性調整

- 前三名不得為同一 `category`  
- 至少保留一個 `indoor` 選項作為天氣突變備案

### 6.5 輸出

interface Recommendation {

  place: Place;

  score: number;

  scoreBreakdown: Record\<string, number\>;  // 除錯用，UI 預設不顯示

  reasons: string\[\];

  warnings: string\[\];

  suggestedDeparture: string;

  suggestedReturn: string;

  backupPlace?: Place;

}

`reasons` 由**規則模板**產生（非 LLM），確保與 `scoreBreakdown` 一致：

// 範例

if (breakdown.schedule \> 0.8) reasons.push(\`現在出發 ${returnTime} 前回到家，接得上午睡\`);

if (breakdown.freshness \> 0.9) reasons.push(\`這個月還沒去過\`);

if (weather.rainProbAfter(15) \> 0.4) warnings.push(\`15:00 後可能下雨\`);

> LLM 可在**呈現層**選擇性地潤飾這些句子，但不得改變其語意，也不得新增規則未產生的理由。

## 7\. AI 輔助建檔流程（v0.2 新增）

目的：把 50 筆地點建檔從「數個週末的苦工」降為「一個晚上的校對」。

### 7.1 流程

1\. 使用者輸入地點名稱（例：「大安森林公園」）

2\. AI 檢索公開資訊（部落格、官網、評論）

3\. AI 輸出 Place 欄位草稿，標記 fieldSources \= "ai\_suggested"

4\. UI 呈現草稿，逐欄位供使用者確認 / 修改

5\. 使用者確認的欄位改為 "ai\_confirmed" 或 "manual"

6\. 存檔

### 7.2 硬性規則

- **AI 產出永遠是草稿，不得直接入庫。** 必須經過步驟 4 的人工確認。  
- **以下欄位 AI 不得填寫，必須手動輸入**：  
  - `driveMinutes`（AI 不知道你家在哪，也不含找車位時間）  
  - `personalRating`  
  - `sweetSpotAge`（這是關於你小孩的判斷，不是關於地點的事實）  
- **AI 對不確定的欄位必須留空，不得猜測。** 寧可空著讓使用者填，也不要填一個看起來合理的錯值。  
- UI 需以視覺標示區分 `ai_suggested`（未驗證）與其他來源，例如虛線邊框或標籤。

### 7.3 建議 prompt 結構

你是一個資料抽取工具。根據提供的網頁內容，抽取以下欄位。

規則：

\- 只輸出 JSON，不要說明

\- 無法從內容確定的欄位，值設為 null，不要猜測

\- energyBurn 與 typicalDurationMin 若無明確依據，一律 null

## 8\. 技術架構

### 8.1 選型建議

| 層 | 選擇 | 理由 |
| :---- | :---- | :---- |
| 框架 | **Next.js (App Router) \+ TypeScript** | 單一 repo 涵蓋前後端，PWA 支援好 |
| 樣式 | **Tailwind CSS** | 快速迭代 |
| 資料庫 | **SQLite (better-sqlite3)** 起步 | 單使用者無需雲端；未來多裝置同步再換 Postgres/Supabase |
| ORM | **Drizzle** | 型別安全、schema 遷移簡單 |
| AI | Anthropic API（僅用於建檔與呈現層） | 不進入決策路徑 |
| 狀態 | RSC \+ 少量 client state | 不需要 Redux |
| 部署 | **Vercel** 或自架 | 初期免費層足夠 |
| 型態 | **PWA（手機加到主畫面）** | 不做原生 App，省掉上架與雙平台成本 |

### 8.3 推薦引擎必須是純函式

export function recommend(

  places: Place\[\],

  visits: Visit\[\],

  context: RecommendContext

): Recommendation\[\]

無副作用、不讀資料庫、不呼叫網路。**這讓演算法可以單獨寫單元測試——調權重是長期持續的工作，沒有測試會越調越亂。**

### Phase 2：累積（1–2 個月）

- [ ] AI 輔助建檔（§7）  
- [ ] 出遊紀錄功能  
- [ ] 地點歷史摘要視圖（§10.2）

- [ ] Stage 3 多樣性  
- [ ] 雨天備案連結  
- [ ] PWA 離線快取

>   
> AI 建檔排在 Phase 2 而非 Phase 1，理由：前 50 筆手動建檔的過程，是你確認欄位設計是否合理的唯一機會。欄位定義穩定後再自動化才有意義。

### Phase 3：擴散（視情況）

- [ ] 呈現層 AI 潤飾與對話式條件調整  
- [ ] 匯出/分享單一推薦（觀察是否有人主動要用）  
- [ ] 多使用者支援（此時才需要真正的帳號系統）  
- [ ] 住宿／包棟延伸（過夜情境，篩選邏輯不同）

### Phase 4：變現（只在有真實他人使用者之後）

- [ ] 聯盟行銷連結（Klook / KKday / Agoda）  
- [ ] 不做展示廣告  
- [ ] 不做業者付費上架

>   
> 變現原則：推薦排序與金錢完全隔離。聯盟連結只出現在使用者**已決定要去之後**的畫面。這條界線一旦破了，產品唯一的資產（誠實）就沒了。

## 12\. 為未來預留的架構決策

1. **`Place` 加 `ownerId` 欄位**（v1 全填同一值）— 未來多使用者不需大改 schema  
2. **推薦引擎純函式化** — 未來 A/B 測試或搬到伺服器端都容易  
3. **`Visit` append-only，永不刪除** — 這是最有價值的資產  
4. **門檻值與權重集中管理** — `thresholds.ts` / `weights.ts`  
5. **地點資料可匯出成 JSON** — 避免被自己的資料庫綁架  
6. **`fieldSources` 從第一天就存在** — 即使 v1 全填 `manual`，Phase 2 導入 AI 時不需 migration

## 13\. 給 Claude Code 的實作備註

- **先做 Phase 1，不要一次生成全部。** 順序：schema → 天氣 → 推薦引擎（含測試）→ UI → seed 資料  
- **推薦引擎務必附單元測試**，至少涵蓋：雨天過濾、午睡時間衝突、多小孩取最低分、最近去過降權、歷史成效權重不超過 5%  
- **`lib/ai/` 不得被 `lib/recommend/` import。** 若需要，加一條 lint rule 強制  
- **UI 用 Tailwind，行動優先**，斷點以 375px 為基準  
- **CWA API key 放 `.env.local`**，透過 API route 代理  
- **seed-places.json 留空結構即可**，實際資料由使用者填入  
- 若對欄位設計有更好建議，**先提出討論再改**——`Place` 的欄位定義是本產品的核心差異化，不是隨意的技術選擇
