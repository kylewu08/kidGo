## 0. 三個貫穿全文的原則

**① 使用者負擔與系統負擔要分開。**
§13.2.6 說「除兩項回饋外，造訪紀錄所有欄位皆為選填」。
這句話的對象是**使用者要填的東西**，不是系統自己知道的東西。
日期、月齡快照、推播建議的時間，這些系統本來就有，存下來不增加任何負擔。
**本文把每個欄位標成「使用者填」或「系統填」**，避免把 §13.2.6 誤讀成「什麼都不能存」。

**② 不可能的狀態要無法表示。**
（例如「有遊具設施」但「適齡層是空的」不該能存在。）
這是先前實作出發點表單時吃過的虧：縣市與鄉鎮拆成兩個狀態，就有辦法組合出
「宜蘭縣三峽區」。合成一個之後那個 bug 連表示都表示不出來。

**③ 每個欄位都要知道自己是怎麼來的。**
§6.2 硬性要求逐欄位追蹤來源。這不是為了好看——**匯入器重跑時要靠它判斷
哪些值可以覆蓋、哪些是使用者確認過的不能動。** 見 §7。

## 1. Place（地點）

### 1.1 身分與來源

| 欄位 | 型別 | 誰填 | 說明 |
|------|------|------|------|
| id | uuid | 系統 | |
| sourceDataset | text | 匯入 | 哪一份開放資料（遊戲場清冊／親子館／公園設施／觀光景點） |
| sourceId | text | 匯入 | 該資料集內的原始主鍵。**與 sourceDataset 合成外部唯一鍵** |
| importedAt / sourceUpdatedAt | text | 匯入 | |
| sourceRemovedAt | text? | 匯入 | 來源資料集不再包含這筆時標記，**但不刪除**——它可能已有造訪紀錄 |

**為什麼要留外部鍵**：重複匯入時要能認出「這是同一個地點」，否則每次匯入都會產生重複資料。

### 1.2 位置

| 欄位 | 型別 | 誰填 |
|------|------|------|
| name / address | text | 匯入 |
| category | enum | 匯入（決定先驗值） |
| lat / lng | real | 匯入 |
| parkingSearchMinutes | int | 先驗，可手動改 |
| usesFreeway | bool | 推導，見 ❓Q2 |

**基準車程不是欄位**（ADR-0013）。它由 `lat/lng` 與住家座標即時導出。
Google 的精算結果若要快取，另立一張帶時間戳的表並在 30 天內刪除，見 §6。

### 1.3 核心判斷欄位（§6.2）

| 欄位 | 取值 | 用於 |
|------|------|------|
| energyBurn 放電強度 | 1–5 | 評分 |
| typicalDurationMinutes 預估停留時長 | 分鐘 | Stage 1 時間過濾、返家時間 |
| bestTimeSlots 適合時段 | 清晨/上午/午睡後/傍晚 的集合 | 作息契合度 |
| **facilityAgeBands 設施適齡層** | `嬰兒/學步兒/學齡前/學齡` 的集合，或 **null＝無遊具設施** | **Stage 1 硬過濾** |
| **runnableSpace 可奔跑空間** | 0–3 | 硬過濾的補償項、評分 |
| **safetyEnclosure 安全封閉性** | 0–3 | **Stage 1 硬過濾**（幼兒階段） |
| **parentEffort 家長負擔** | 1–5 | **Stage 1 硬過濾**（超過偏好上限） |
| hasAirConditioning 有無冷氣 | bool | 夏季評分 |
| indoorType 室內外 | 室內/戶外/混合/有遮蔽戶外 | 天氣過濾與評分 |
| shadeLevel 遮蔭 | 0–3 | 高溫補償 |
| strollerFriendly 推車友善 | bool | 硬過濾 |
| suitableAgeMonths 適用年齡範圍 | `{min,max}` 月齡 | 硬過濾。見 ❓Q1 |

**`facilityAgeBands` 用「集合或 null」而不是「布林 + 集合」**：
後者能表示「有設施但適齡層是空的」這種不可能的狀態。
null 明確代表無遊具設施（美術館、步道、沙灘），非空集合代表有設施且適合這些年齡層。

**年齡層對應月齡**屬於領域參數，不進資料庫：
嬰兒 0–12m／學步兒 12–36m／學齡前 36–72m／學齡 72m+。

### 1.4 狀態與資料品質

| 欄位 | 型別 | 說明 |
|------|------|------|
| fieldSources | JSON map | 每個欄位一個值：`category_prior` / `ai_suggested` / `manual` / `visit_corrected` |
| dataSuspect | bool | 使用者按「看了覺得不適合」時標記（ADR-0011） |
| dataSuspectReason | text? | 設施不適齡／太遠／看起來很小 |
| lastVerifiedAt | text? | |

**「候選 / 已驗證」不存成欄位，由造訪紀錄筆數導出。**
存成欄位會與紀錄不同步，而它是可以零成本算出來的。

### 1.5 從 v0.2 移除的欄位

`sweetSpotAge`、`crowdLevel`、`costPerFamily`、`hasWaterPlay`、`hasNursingSpace`、
`quietHours`、`personalRating`、`indoorBackupPlaceIds`、`ownerId`

理由：v1.0 §6.2 的語彙表沒有它們，而 §7.2 的評分因子也不再引用。
`ownerId` 是 v0.2 為未來多使用者預留的，v1.0 把多使用者放到 Phase 3——
**在單使用者的 SQLite 上加一欄是幾秒鐘的 migration，不值得現在就背著一個永遠是 "local" 的欄位。**

## 2. Child（小孩）

**與現有實作幾乎相同**，v1.0 §6.1 的三個概念（作息階段、午睡窗、行動力）
與 v0.2 一致，§11.3 的月齡對照表也一字未改。

| 欄位 | 誰填 |
|------|------|
| name / birthDate | 使用者 |
| napStage 作息階段 | 由月齡推導，可覆寫 |
| napWindows 午睡窗 | 由階段推導，可覆寫 |
| wakeTime / bedTime | 使用者 |
| mobility 行動力 | 使用者 |
| notes | 使用者，選填 |

**§13.2.5 是程式碼組織的約束不是 schema 的**：小孩約束邏輯（月齡推導作息、
計算可用時間窗、體力上限）要獨立成模組，供未來的過夜規劃模式共用。
Schema 不變，但 `lib/child-constraints/` 這類模組要與 `lib/recommend/` 分開。

## 3. FamilyPreference（家庭偏好）— 全新

單列表，與 HomeBase 同樣的形狀。

| 欄位 | 取值 | 來源 |
|------|------|------|
| outdoorTendency 戶外傾向 | -2 … +2（負＝偏室內） | 初始三題 |
| maxParentEffort 家長負擔上限 | 1–5 | 初始三題 |
| requiresMeal 是否需含用餐 | bool | 初始三題 |

**類別權重另立一張表**，因為它有學習狀態要追蹤：

| 欄位 | 說明 |
|------|------|
| category | 主鍵 |
| learnedWeight | 由回饋累積 |
| manualWeight | **非 null 時優先，且學習不再更新它**（§6.3） |
| sampleCount | **少於 8 筆時不套用學習權重**（§6.3） |
| lastUpdatedAt | |

**為什麼 sampleCount 要存而不是即時算**：§6.3 硬性要求 UI 顯示學習依據
（「戶外公園 +35%，依你最近 12 次選擇」）。那個「12 次」必須拿得到。

**學習訊號的方向**（§6.3）：採納 ↑、跳過 ↓（幅度小於採納）、回饋「順利」↑↑。
實際幅度是領域參數，集中在參數檔（§13.2.10）。

## 4. Suggestion（推播建議）— 全新，而且是樞紐

這張表是整個回饋迴路的中心。它記錄「系統送出了什麼」，
而 §6.4 說「到離時間：取當日推播的建議值，不要求使用者提供」——
**那個「建議值」就存在這裡。**

| 欄位 | 誰填 | 說明 |
|------|------|------|
| id | 系統 | |
| sentAt | 系統 | |
| kind | 系統 | `morning`（第一則）/ `afternoon`（第二則附帶的下午建議） |
| primaryPlaceId | 系統 | 主建議 |
| backupPlaceId | 系統 | 備案（室內） |
| explorePlaceId | 系統 | 探索槽。**推播不顯示，落地頁才顯示**（§7.3 vs §9.1） |
| suggestedDeparture / suggestedReturn | 系統 | 具體到分鐘（§9.1） |
| noOutingReason | 系統 | 「今天不要出門」路徑時填，其餘為 null |
| contextOverrideId | 系統 | 若套用過一次性情境（§5） |
| response | 使用者 | 見下 |
| respondedAt | 使用者 | |
| responseNote | 使用者 | 選填 |

### response 的四個值（ADR-0011）

| 值 | 對偏好學習的影響 | 對地點的影響 |
|----|-----------------|-------------|
| `went` | 類別權重 ↑ | 產生一筆 Visit |
| `stayed_home` | **無**（這是生活的問題不是推薦的問題） | 無 |
| `went_elsewhere` | 類別權重 ↓（幅度小） | 若願意說去了哪，記錄比較性訊號 |
| `looked_unsuitable` | **無** | **標記 dataSuspect，降低曝光** |

**`looked_unsuitable` 不影響偏好，這是 ADR-0011 的核心主張**：
它是資料品質訊號不是偏好訊號。混在一起會讓偏好模型學到錯的東西。

## 5. Visit（造訪紀錄）

**永不刪除**（§6.4）。由 `Suggestion.response = went` 產生，也可手動補建。

| 欄位 | 誰填 | 必填 |
|------|------|------|
| placeId / date | 系統 | ✓ |
| suggestionId | 系統 | 由推播產生時有值 |
| childAgesMonths | 系統 | ✓ **月齡快照，不可由生日反推** |
| **durationFeeling** | **使用者** | ✓ 比較短 / 差不多 / 比較久 |
| **outcome** | **使用者** | ✓ 順利 / 普通 / 崩潰 |
| arrivedAt / leftAt | 系統（取推播建議值） | 選填 |
| actualDriveMinutes | 使用者 | 選填，**Phase 1 不收集** |
| notes | 使用者 | 選填 |
| contextOverrideId | 系統 | 若當次套用過情境覆寫 |
| weatherSnapshot | 系統 | 選填，見 ❓Q4 |

**唯二必填就是那兩個由推播按鈕產生的欄位**，符合 §13.2.6。
其餘不是「不存」，是「不要求使用者提供」。

### durationFeeling 怎麼修正 typicalDurationMinutes

這是相對值不是絕對值，所以修正是漸進的：
連續多次「比較短」就下修預估時長，反之上修。
**每次修正的幅度與所需筆數是領域參數**，集中管理。見 ❓Q3。

## 6. 支援性資料表

| 表 | 用途 |
|----|------|
| **ContextOverride** | §8 的一次性情境。存 `rawInput`（使用者打的字）、`overrides`（型別與範圍驗證後的結構化值）、`explanation`（UI 顯示用）。**僅對本次有效，不寫入 FamilyPreference** |
| **CalendarDay** | 連假判定（§10.2）。政府行政機關辦公日曆表，年度快取。`date` → `一般平日/一般週末/國定假日/連假` |
| **PushSubscription** | Web Push 的 endpoint 與金鑰 |
| **RouteCache** | Google 精算結果的短期快取。**必須帶 `fetchedAt` 並在 30 天內刪除**（ADR-0013 / Google ToS） |

`RouteCache` 需要一個定期清理的排程。**這是合規要求不是效能優化**，
所以清理失敗應該要能被發現，不能靜默。

## 7. 匯入器的 upsert 規則（我認為最容易出錯的一塊）

重複匯入時，**已經被人確認過的值不能被類別先驗值蓋回去**。
這正是 `fieldSources` 存在的理由。

```
以 (sourceDataset, sourceId) 比對：

找不到 → 新增，全部欄位標記 category_prior

找到了 → 逐欄位判斷：
   fieldSources[欄位] == category_prior  → 可以覆蓋
   其他（manual / visit_corrected / ai_confirmed）→ 保留，不動

來源不再包含這筆 → 標記 sourceRemovedAt，不刪除
```

**不刪除的理由**：那筆地點可能已經有造訪紀錄。刪掉它會讓紀錄變成孤兒，
而 §6.4 說紀錄永不刪除。這與現有實作對 Place 的刪除防護是同一個道理。

匯入是**冪等**的：同樣的來源資料跑兩次，結果必須完全相同。
這需要測試守著，因為它壞掉的方式很安靜——你要等到某天發現自己改過的值不見了。

## 8. 推薦流程用到的資料流（確認模型撐得住 §7.1）

```
全部地點（半徑內，數百筆）
   │  幾何估計 × 日型係數        ← lat/lng + CalendarDay，零 API
   ▼
Stage 1 粗篩（門檻放寬 20%）
   │  ~ 個位數到數十筆
   ▼
Stage 2 初評（用粗估車程）
   │  取前 8 名
   ▼
精算：Routes API 去程 + 回程分別查   ← 寫入 RouteCache
   │
   ▼
Stage 1 車程條件重檢 + Stage 2 重算
   ▼
Stage 3 多樣性 → 主建議 / 備案 / 探索槽
```

**去程與回程必須分開查**（§7.1）：早上出發與下午返程的路況不同，
而「能否在午睡前返家」正是依賴回程。這代表 `RouteCache` 的鍵要含方向與出發時刻。

## 已確認的五項取捨

原本標為待確認的五點，結論記在 [ADR-0014](adr/0014-data-model-decisions.md)：

1. **`suitableAgeMonths` 與 `facilityAgeBands` 兩者都保留** —— 前者是「這個地方」適合幾歲，
   後者是「現場的遊具」適合幾歲。步道沒有遊具但仍不適合六個月大的嬰兒
2. **`usesFreeway` 用直線距離門檻判斷**，門檻為領域參數
3. **`durationFeeling` 至少 3 筆同方向才調整，每次 ±15%，且只動仍為類別先驗的值**
4. **Visit 保存天氣快照** —— 零使用者負擔，而且事後補不回來
5. **`outdoorTendency` 用 −2…+2 五段** —— 離散值在 UI 上講得清楚

### 順帶修正了 ADR-0013 的一個過度指引

ADR-0013 原本寫「幾何估計的誤差要刻意偏向低估」。
檢視 Q2 時發現這與 §7.1 的設計重複了——緩衝已經放在門檻上（「放寬約 20%」），
在估計值裡再偏移等於加了第二層無法單獨調整的緩衝。

而且放行過多不是免費的：**Stage 2 只挑前 8 名去精算，
一個被低估的遠地點會擠掉一個真正到得了的近地點。**

修正後：幾何估計與 `usesFreeway` 都**求準**，緩衝只放在粗篩門檻那一個參數上。
