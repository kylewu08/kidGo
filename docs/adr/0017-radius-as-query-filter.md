# ADR-0017：半徑改為查詢時的篩選條件，匯入器不依賴住家位置

- **狀態**：已採納
- **日期**：2026-08-26
- **相關**：設計架構書 v1.0 §P4、§10.1、§7.1
- **取代**：[ADR-0009](0009-import-radius-not-counties.md) 中「匯入」與「基準車程計算」的兩層切分
  （「用直線半徑而非縣市界」這個核心判斷仍然有效）

## 背景

ADR-0009 把匯入拆成兩層：全臺資料照收（免費、離線），
只對住家直線半徑 75 km 內的地點**批次計算基準車程並存起來**（消耗 Routes API 額度）。
半徑存在的理由是額度。

之後 [ADR-0013](0013-geometric-baseline-drive-estimate.md) 把基準車程改成幾何估計，
匯入階段完全不呼叫 Google。實作時進一步確認：

- `places` 表**沒有**基準車程欄位，也沒有距離欄位，只有 `lat` / `lng`
- `baselineDriveMinutes()`（`lib/domain/drive-estimate.ts`）是每次決策當下從座標算的
- 「批次計算基準車程」這個動作在今天的程式碼裡**已經不存在**

也就是說，ADR-0009 立論的那個成本已經被 ADR-0013 抽掉了。
半徑今天唯一還在影響的是資料庫筆數與每次決策要走訪的筆數。
這個前提變了，就得重新問一次半徑該放在哪一層。

## 被考慮的選項

### 選項 A：匯入時就丟掉半徑外的地點
- 優點：資料庫維持數百筆、小於 1 MB；匯入跑得快；`listPlaces()` 不必改；
  人工檢視資料時沒有永遠用不到的雜訊
- 缺點：**匯入器的輸出變成 `f(來源資料, 住家位置)`**。
  這與[資料模型草案](../資料模型草案.md) §7 的 upsert 規則直接衝突——
  一筆地點從結果中消失會有兩個不同的原因（來源砍了它／使用者搬家使它落到半徑外），
  前者該標 `sourceRemovedAt`，後者不該，因為那個地點還在，只是變遠了。
  而它若已有造訪紀錄，§6.4 說永不刪除，也不能真的丟掉。
  換住家或調高車程上限都要重新連網跑一次完整匯入

### 選項 B：全臺照收，半徑改成查詢時的篩選條件
- 優點：匯入器的輸出是 `f(來源資料)`，與住家無關，冪等測試不必模擬住家狀態；
  換住家或調高 `maxDriveMinutes` 改個數字就生效，不碰網路；
  Phase 3 過夜模式換一個半徑即可，用的是同一份資料；
  **半徑不需要任何欄位**——距離本來就是從 `lat` / `lng` 算出來的，不是存下來的
- 缺點：資料庫粗估兩三萬筆、10–20 MB；匯入跑得久；
  `listPlaces()` 需加一道 lat/lng 邊界框條件，否則每次決策都把全臺讀進記憶體

## 決定

選 **B**，由使用者於 2026-08-26 確認。

最關鍵的理由是選項 A 缺點的第一項：**A 讓匯入器的正確性取決於住家位置。**
為了省下 10–20 MB，要在匯入器裡多養一組區分「來源移除」與「移出半徑」的狀態機，
而它壞掉的方式很安靜——搬家後重跑匯入，某些已有造訪紀錄的地點被誤標為來源已移除。
B 沒有這個狀態，因為它根本不記錄半徑這件事。

效能不是選 B 的代價：兩三萬筆的 lat/lng 邊界框查詢在 SQLite 是毫秒級，
而推播是伺服器端一天執行一次。

## 後果

- **得到**：匯入器成為純粹的「來源資料 → 本地資料」轉換，
  可以在沒有住家設定的情況下跑，也可以獨立測冪等性
- **得到**：住家位置與車程上限成為真正的執行期參數
- **放棄**：資料庫裡會有大量永遠不會出現在推薦裡的地點。
  人工檢視資料時要記得先套半徑，否則看到的是全臺
- **要做**：`listPlaces()` 必須加上邊界框條件，且半徑要由 `maxDriveMinutes` 推導
  而不是寫死 75 km——ADR-0009 的 75 km 本來就是從 45 分鐘上限推回來的一個例子值
- **何時重新考慮**：若全臺筆數遠超預期（十萬筆以上）使得單次查詢明顯變慢，
  或 Phase 3 之後出現「同時對多個出發點推薦」的需求使得邊界框失效，
  屆時該考慮的是加索引或預先分群，而不是回到 A——
  A 的問題是正確性，不會因為資料變大而改善
