# ADR-0008：改採設計架構書 v1.0，以演進而非重寫的方式遷移

- **狀態**：已採納
- **日期**：2026-08-25
- **相關**：全部既有 ADR；[`docs/設計架構書-v1.0.md`](../設計架構書-v1.0.md)
- **取代**：以 [`docs/archive/設計架構書-v0.2.md`](../archive/設計架構書-v0.2.md) 作為需求來源這件事

> **這份 ADR 是 v0.2 與 v1.0 之間的對照表。**
> 沒有它，任何人（包括未來的 AI 協作工具）打開這個 repo 都會看到一堆
> 對不上現行規格的程式碼與註解，卻不知道哪些是刻意保留、哪些是還沒改。

## 背景

Phase 1 依 v0.2 實作完成後，使用者於 2026-08-25 提出設計架構書 v1.0，
並表示「跟我想像的差很多，可能要打掉重練」。

v1.0 不是 v0.2 的修訂，是**不同的產品定義**。三個根本改變：

| | v0.2 | v1.0 |
|---|------|------|
| 資料怎麼來 | 使用者手動建 40–60 個地點 | **零建檔啟動**：開放資料自動匯入，初始輸入僅住家地址與小孩生日 |
| 答案怎麼交付 | 打開 App 看首頁「今天去哪」 | **週末早晨的推播**；App 是設定與回饋介面 |
| 決策模型 | 6 個評分因子 | 7 個因子（新增家庭偏好），Stage 1 新增三條硬過濾 |

其中兩項寫成了驗收標準：「若仍需手動建檔才能使用，Phase 1 未完成」、
「連續四個週末，在未主動開啟 App 的前提下完成決策」。

## 被考慮的選項

### 選項 A：打掉重練
- 優點：不必背既有程式碼的包袱，可以完全照 v1.0 的形狀重新設計
- 缺點：會丟掉 v1.0 **明文要求而且已經蓋好**的東西——純函式引擎架構、
  lint 強制的 AI 邊界、門檻與權重集中管理、2700 行的引擎與測試、
  CWA 串接與 368 筆鄉鎮對照表、Routes API 客戶端。
  這些正是重蓋最貴的部分

### 選項 B：演進——換掉資料來源與交付形式，加寬領域模型
- 優點：保留 v1.0 仍然要求的地基；改動集中在真正變掉的地方
- 缺點：需要一份明確的對照表，否則新舊混雜會比重寫更難維護
  （本文就是為了消除這個缺點）

## 決定

選 **B**，由使用者於 2026-08-25 確認。

判斷依據：v1.0 的 §7.6（引擎架構約束）與 §13.2（不可違反的約束）
幾乎是在描述現有實作。**規格改變的是產品，不是地基。**

### 需擴充但骨架可用

- **`lib/routes/`** — Routes API 選擇正確（§10.3 確認 Legacy API 不得採用）。
  要加：兩種計費層級、**去程與回程分開計算**、日型係數降級、不走國道跳過查詢
- **`lib/recommend/`** — Stage 1 加三條硬過濾、Stage 2 換權重加一個因子、
  Stage 3 從 Phase 2 提前到 Phase 1

| # | 衝突 | v1.0 依據 |

## 後果

- 保留：`lib/recommend/`、`lib/weather/`、`lib/routes/` 的骨架與大部分測試
- 重做：`app/` 約一半（地點新增表單、首頁降級）、`lib/db/` 的 schema
- 新增：匯入器、家庭偏好、推播子系統、一次性情境輸入

### 執行順序（§13.1）

**第一步不是寫程式，是提出資料模型草案供討論。**
之後：匯入器 → 天氣 → 推薦引擎 → 推播 → 落地頁。

### 什麼情況下該重新考慮

若資料模型草案完成後發現「保留下來的引擎骨架需要大幅改寫才能容納新模型」，
那代表選項 B 的前提不成立，此時應該回頭認真評估選項 A。
**判斷時機是草案定案後、動工之前**，不是做到一半才發現。
