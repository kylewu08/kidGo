# ADR-0012：住家位置用縣市／鄉鎮下拉，不接 Geocoding API

- **狀態**：已採納（第一階段）
- **日期**：2026-08-25
- **相關**：設計架構書 v1.0 §12（「僅輸入住家地址與小孩生日」）、[ADR-0006](0006-homebase-stores-county.md)

## 背景

v1.0 §12 的驗收標準一寫「僅輸入住家地址與小孩生日」。
但地址轉座標需要 **Geocoding API**——那是 Routes API 之外的另一支服務，
需要另外啟用、另外計費、另外設配額上限。

而 CWA 鄉鎮天氣預報本來就需要知道鄉鎮（[ADR-0006](0006-homebase-stores-county.md)），
`lib/weather/townships.ts` 已經有全臺 368 個鄉鎮市區的名稱與座標。

## 被考慮的選項

### 選項 A：縣市／鄉鎮兩段式下拉，選完帶出座標，可手動微調
- 優點：不需多開一支 API；少一份帳單風險與配額要管；
  鄉鎮資訊本來就要收集（天氣需要）；**已經實作完成可直接沿用**
- 缺點：多一個「微調座標」的步驟；鄉鎮代表點與實際住家有數公里誤差

### 選項 B：啟用 Geocoding API，直接打地址
- 優點：最貼近 §12 的字面；輸入體驗最順
- 缺點：多一支 API 要管理、要設配額；多一個外帳單風險點；
  而且鄉鎮仍然要另外決定（天氣需要），並沒有省掉那一步

## 決定

選 **A**，由使用者於 2026-08-25 確認，並明確標示為**第一階段**的做法。

關鍵理由：**選 B 並不能省掉鄉鎮選擇**——CWA 需要鄉鎮，而從座標反推鄉鎮
又需要另一次查詢或一份邊界資料。B 增加了依賴卻沒有減少步驟。

座標誤差的影響有限：住家座標用於天氣（鄉鎮層級本來就是那個精度）
與車程起點（數公里的差距在粗篩階段可忽略，精算階段影響數分鐘）。
而且**只需要設定一次**，願意精確的人可以貼上實際座標。

## 後果

- 得到：金鑰仍只需 Routes 一支；現有的出發點設定畫面可直接沿用
- 放棄：§12 字面上的「輸入地址」。實際輸入的是縣市＋鄉鎮＋可選的座標微調
- 這是**第一階段**的決定。若之後因其他需求已經啟用 Geocoding，
  可回頭把地址輸入補上，屆時本文應被新的 ADR 取代

### 什麼情況下該重新考慮

1. 實際使用發現鄉鎮代表點與住家的距離造成推薦明顯偏差
   （判斷方式：比較用鄉鎮代表點與實際座標算出的精算車程差幾分鐘）
2. 專案因其他功能已經需要 Geocoding API，此時邊際成本降為零
