# ADR-0018：做「快速標記」掛在推播回饋之後，不做獨立的偏好滑卡

- **狀態**：已採納
- **日期**：2026-08-28
- **相關**：設計架構書 v1.0 §6.3、§6.4、§7.2、§7.4、§9.2、§9.3、P2

## 背景

冷啟動問題是真的。匯入的地點六個決策欄位（`energyBurn`、`parentEffort`、
`safetyEnclosure`、`typicalDurationMinutes`、`shadeLevel`、`hasAirConditioning`）
全部來自 `category-priors.ts` 那 11 列查表，而歷史成效固定 5%。
零紀錄時，排序實際上只剩距離、作息與類別在起作用。

還有一個更具體的缺口：**使用者其實已經去過匯入地點中的一部分，
而那個資訊只存在他腦袋裡。** 系統要靠一週一次的造訪，花很久才能重新發現。

「一開始讓使用者評十部電影」在推薦系統裡是成熟做法（冷啟動偏好誘導），
Netflix 與 Spotify 都用。方向合理，問題在於這個產品該收哪一種訊號。

## 被考慮的選項

### 選項 A：獨立的偏好滑卡頁面，持續餵養偏好

使用者沒事就逐筆滑「喜歡／不喜歡」，逐漸建立偏好。

三個缺點，第一個是結構性的：

1. **供給量撐不起這個介面。** Tinder 成立的前提是供給無限。
   套完入場測試後住家半徑內大概 100–300 筆，一個晚上就滑完，
   之後沒東西可推。**這與 P4「窄而深」互斥**，不是調參數能解的
2. **滑卡是在「無成本的世界」裡表態，真實決策是在「有成本的世界」裡取捨。**
   使用者會對漂亮的森林步道右滑，然後實際上帶小孩去家門口那個公園——
   因為那天小孩要抱、家長負擔 5、開車 50 分鐘。前者測到審美偏好，
   後者才是行為偏好。而現有的兩個學習訊號（「去了／沒去」、
   第二則推播的三次點擊）**都是行為訊號**，這是優點不是限制
3. **違反 P2。** 滑卡的價值定義上必須主動打開 App 才拿得到

補充一個削弱其投報率的事實：家庭偏好在 §7.2 只佔 **15%**
（`weights.ts` 的 `familyPreference: 0.15`），而 §7.4 防線一規定
雨天、體感 32 度以上、或硬過濾後存活少於 5 個時**整個歸零**。
把偏好測得更準，改變的是那 15% 內的排序，不是候選集是誰。

### 選項 B：快速標記，掛在推播回饋之後（採用）

不問「你喜歡嗎」，改問「你們去過嗎」：

```
今天建議大有梯田生態公園。
順便問一下，這三個你們去過嗎？（可跳過）
  [ 去過，還不錯 ] [ 去過，不適合 ] [ 沒去過 ] [ 想去 ]
```

- 收的是**已發生的事實**，不是假設性的表態
- 有自然終點：腦袋裡的存量是有限的，滑完就停，不需要無限供給
- 搭在既有推播上，不新增主動入口

### 選項 C：什麼都不做，等造訪紀錄自然累積

- 優點：零實作成本，完全不冒污染訊號的風險
- 缺點：頭幾個月推薦品質低，使用者可能在回饋迴圈轉起來之前就流失。
  而 §9.3 說採納率是「長期主力訊號」——沒有採納就沒有訊號，這是個死結

## 決定

選 **B**，由使用者於 2026-08-28 確認。

最關鍵的理由是**訊號的性質**：選項 A 收集的是假設性偏好，
會與行為訊號在同一組類別權重裡打架；選項 B 收集的是已發生的事實，
補的是一個真實存在的缺口（使用者去過但系統不知道的地點）。

### 硬性約束

1. **不得寫入類別權重或任何評分因子。** 只寫入造訪狀態與「想去」標記。
   這是本 ADR 的核心約束——一旦它能改權重，選項 A 的所有問題就從後門回來了
2. **「想去」僅作為探索槽在**選定類別之後**的排序依據，
   不得作為選擇依據。** §7.4 防線二規定探索槽優先分配給**偏好之外的類別**；
   「想去」本身就是偏好，用它挑類別會讓防同溫層失效——
   使用者不會把室內地點加進願望清單，於是雨天手上還是只有沒驗證過的牌
3. **掛在推播回饋之後，不做獨立入口。** 與 §9.2「第二則推播不得改為
   導流通知」是同一個道理
4. **可整批跳過，且跳過不得影響其他流程**（§9.3：系統不依賴使用者的勤勞）

## 後果

- **得到**：冷啟動有解，且沒有新增任何「必須打開 App 才有價值」的東西
- **放棄**：偏好測不準。接受——它只佔 15% 且經常歸零
- **待決（本 ADR 不決定）**：「去過，還不錯」該產生什麼？
  §6.4 要求造訪紀錄保存**當次的小孩月齡快照**與情境覆寫，
  而回溯標記兩者都沒有——使用者記不得是哪個月去的。
  所以它不能直接寫成一筆 `Visit`。可能的做法是加一個「回溯」旗標
  並允許月齡快照留空，但那要改資料模型，依 AGENTS.md 須先討論
- **何時重新考慮**：若造訪紀錄累積之後發現冷啟動根本不是瓶頸，
  這個機制可以整個拿掉——它是補償措施，不是核心

## 附記：關於「去過且不錯」跨使用者共享

討論中提出過讓不同使用者共享「去過且不錯」的標記，以發揮社群力量。
**本 ADR 不涵蓋這個方向**，理由是它牽涉 §12 列為 Phase 3 的多使用者支援
與帳號系統，且 v1 明確不做社群／分享。

但有一點值得先記下來，因為它會影響本 ADR 的資料設計：
真正適合共享的是**地點欄位的修正**（「這個公園有圍欄」——關於公共場所的
客觀事實），而不是**造訪紀錄**（「我家小孩上週六在這裡很順利」——
牽涉小孩月齡與家庭作息，且結果高度依賴該家庭的特定小孩）。
若未來要做，`fieldSources` 這套機制已經預留了位置。
