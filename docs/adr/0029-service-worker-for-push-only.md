# ADR-0029：Service Worker 只負責推播，不做離線快取

- **狀態**：已採納
- **日期**：2026-09-04
- **相關**：[ADR-0003](0003-pwa-over-native-app.md)、[ADR-0023](0023-public-image-without-source.md)、設計架構書 §9.4、§13.2 第 8 條、P8、P9

## 背景

§9.4 是規格裡少數標「必讀」的一節：**iOS 的 Web Push 只在 PWA 被加入
主畫面後可用**。PWA 的三件事前兩件已經做完（manifest 與圖示 `357323b`、
「加入主畫面」引導 `79230af`），剩 Service Worker——`push` 事件只在 SW
裡收得到，沒有它就沒有推播，而推播是這個產品的主要形態（§1.3）。

`push_subscriptions` 資料表（`lib/db/schema.ts`）從 v1.0 的 schema 就存在，
但**沒有任何寫入路徑**。訂閱只有瀏覽器做得到，而週末早晨那則推播是伺服器
在無人互動下送出的（§13.2 第 1 條的第二個理由）——它得知道要送去哪裡。

一支 SW 一旦存在，就會被期待順便做四件事。這份 ADR 記的是**四個都刻意
只做一半或不做**的理由。

## 決定一：不做離線快取

### 被考慮的選項

**A. cache-first 的 app shell + 快取上一次的 `/today`**
真正兌現 P9「離線可用」在瀏覽器端的意涵。

**B. 只做推播，離線另議**（選了這個）

### 理由

P9 的原文是「核心資料本地優先」，那件事由伺服器端的 SQLite 完成，
**已經成立**——這個產品的資料不在雲端，NAS 斷網也查得到。

而快取 `/today` 會**製造一個新的誠實問題**：離線時顯示的是昨天算出來的
建議，「今天大雨、體感 34°C，建議在家」放到隔天就是假的。P8 說誠實不可
交易，而「過期的建議要怎麼標示才不會被誤讀」是一個獨立的設計問題，
不該在做推播的路上順手決定。

**離線不是不做，是還沒決定怎麼做才誠實。**

## 決定二：手寫 SW，不用 next-pwa / Serwist

Next 的官方 PWA 指南推薦 Serwist 做離線快取。但**它們的價值在於自動產生
precache 清單**，而決定一說了我們刻意不 precache。扣掉那一塊，剩下的是
`push` 與 `notificationclick` 兩個 handler，五十行。

同 `lib/import/zip.ts` 與 `scripts/generate-icons.mjs` 的判斷：
為五十行引一個會接管建置流程的依賴，對一個要離線跑在 NAS 上的專案不划算。

## 決定三：送出用 `web-push` 這個依賴

**這裡與決定二相反，而理由是同一個判準的另一邊。**

送一則推播要做 ECDH 金鑰協商、HKDF 導出金鑰、AES-128-GCM 加密內容，
再用 ES256 簽一個 VAPID JWT。這是密碼學，而且是**寫錯了也照樣「看起來
能跑」**的那種——瀏覽器只會靜默地丟掉解不開的訊息。

自己寫的代價不是六十行，是把整個產品的主要形態押在一份沒有人審過的
加密實作上。「不引依賴」從來不是原則，是對成本的估算；這裡估算的結果相反。

## 決定四：VAPID 公鑰用一般環境變數，不用 `NEXT_PUBLIC_`

Next 的慣例（與官方 PWA 指南的範例）是 `NEXT_PUBLIC_VAPID_PUBLIC_KEY`。
**在這個專案會壞。**

`NEXT_PUBLIC_` 是**建置期**替換：值在 `next build` 當下被寫死進 bundle。
而 ADR-0023 之後，映像是 GitHub Actions 建的，CI 上沒有、也不該有 NAS 的
`.env`。結果是瀏覽器拿到字串 `undefined`，而**失敗點在
`applicationServerKey` 解碼**——錯誤訊息完全指不到「金鑰沒設」。

被否決的替代方案是「把公鑰當 build arg 傳進 CI」：那會讓換一把金鑰
變成重建一次映像，而且金鑰從此存在 GitHub secrets 與 NAS 兩個地方。

改成由伺服器元件在**請求時**讀出來、透過 props 傳給前端。公鑰本來就是
要給瀏覽器看的，經由 props 傳過去沒有任何損失，換來的是「改 `.env` 重啟
就生效」。

## 後果

**得到的**：`push_subscriptions` 有了寫入路徑；首頁可以訂閱、取消、
送一則測試通知——那顆按鈕的存在理由是**驗掉 §9.4 那個只有真機驗得掉的
未驗事項**（加入主畫面之後 iOS 到底收不收得到）。

**放棄的**：離線仍然只有伺服器端那一半。SW 沒有 `fetch` handler，
斷網時開 App 就是瀏覽器的離線頁。

**還缺的**：週末早晨那則**還不會自動送出**——排程與規則模板（§9.1）
還沒做。UI 上分兩處明講這件事，P8 不允許讓人以為訂閱完就會收到。

**什麼情況下該重新考慮**：
- 決定一，在「過期建議如何標示」有結論之後——那時 `fetch` handler 值得加
- 決定二，若哪天真的要 precache，Serwist 的成本就變成合理的
- 決定四**不該被重新考慮**，除非映像改成在 NAS 上建置。看到
  `NEXT_PUBLIC_VAPID_PUBLIC_KEY` 這個名字被改回去時，症狀會是
  「本機好好的，線上訂閱不了」
