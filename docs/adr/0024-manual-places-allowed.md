# ADR-0024：允許手動新增地點，但覆蓋率診斷只計算匯入資料

- **狀態**：已採納
- **日期**：2026-09-01
- **相關**：設計架構書 v1.0 P1、§10.1、需求補充 01 §C
- **偏離**：§10.1「使用者不手動建立**任何**地點」

## 背景

使用者舉了兩個他實際跑過的行程：

```
1. 8:00 出門 → 9:00 抵達和平島公園親子泳池 → 玩 1 小時
   → 10:30 洗完澡回程 → 12:00 到家睡午覺
2. 同樣的時間結構，目的地是基隆的親子館
```

查資料庫的結果：

| | 筆數 |
|---|---|
| 和平島公園 | **0** |
| 親子館（全國） | **0**（等 TGOS 座標） |
| 任何泳池／戲水地點 | **0** |
| 真正在基隆市的地點（用座標篩） | **10，全是圖書館** |

**使用者兩個真實行程的目的地，系統一個都不知道存在。**

（順帶查到一個容易誤判的地方：用 `address like '%基隆%'` 會撈到 31 個
「基隆公園」，但那些是臺北市士林區沿**基隆河**的綠地。用座標篩才看得出
基隆市實際只有圖書館。）

落差短期補不上：基隆市沒有公園的開放資料集，而「水域遊憩／泳池」
這個類別根本還沒有來源。

## 規格衝突

設計架構書講了兩次，第二次用了「任何」：

```
P1     使用者不手動建立地點
§10.1  使用者不手動建立任何地點。
```

但**資料模型早就預期了這件事**：

```ts
lib/db/schema.ts
| "manual"; // 使用者自行新增（非匯入）      ← SourceDataset
| "manual"                                  ← FieldSource，強度高於匯入器
```

## 怎麼讀那句話

§10.1 那句的下一句是「初始輸入僅住家地址與小孩生日，完成後系統即可產出
推薦」——**它描述的是啟動時的保證，不是永久的禁令**。P1 要防的是那種
「輸入 50 個地點才開始有用」的產品。

而使用者把去過的地方記下來，不是建目錄，是補一個匯入器搆不到的事實。
需求補充 01 §C（快速標記）已經確立了同樣的原則——使用者手上有系統沒有的
知識——只是它假設那些地點已經在資料庫裡。

## 被考慮的選項

### 選項 A：嚴格照規格，等匯入器涵蓋
否決。基隆公園沒有資料集、泳池類別沒有來源，這不是「再等一季」的問題。
而且期間使用者每次看到推薦，都少了他最常去的那幾個地方。

### 選項 B：開放手動新增，不加限制
**真實的風險**：手動新增一旦成為補資料缺口的辦法，匯入器就不會再進步。
覆蓋率診斷存在的目的正是逼資料擴充；如果使用者可以自己補洞，
診斷會慢慢變綠而真正的覆蓋率沒有改善。

### 選項 C：開放手動新增，但診斷只算匯入資料（採用）

## 決定

允許手動新增地點，並帶三項約束：

1. **`sourceDataset` 為 `manual`，欄位來源標 `manual`。**
   匯入器的覆蓋上限是 `source_data`，所以它永遠不會覆蓋手動填的值
   （`lib/import/upsert.ts` 既有規則，不需修改）。

2. **覆蓋率診斷排除 `manual` 來源。**
   這是選項 B 那個風險的解藥：手動地點會出現在推薦裡（它們是真的地方），
   但**不會讓診斷變綠**。缺口繼續看得見，匯入器該補的還是要補。

3. **手動地點不繞過任何硬過濾。** 它跟其他地點一樣要通過 Stage 1。
   「我加的地方一定要推給我」會讓引擎失去意義。

**P1 的保證不變**：一個地點都不新增，系統仍然可用。手動新增是選項，
不是前提——這正是 §10.1 那句話真正在保護的東西。

## 後果

- 需要一個新增／編輯地點的路徑。**本 ADR 不決定它的形態**
  （UI 或腳本），只確立「可以做」
- 覆蓋率診斷的數字會與資料庫總數不一致。這是刻意的，
  診斷的輸出應標明它算的是匯入資料
- 手動地點的欄位由使用者判斷。§11 說先驗值不得自行推導，
  但那約束的是**程式**——使用者對自己去過的地方就是領域權威

## 什麼情況下該重新考慮

若手動地點的數量開始超過匯入地點的一定比例，代表匯入器的覆蓋出了系統性
問題，那時該處理的是資料來源，不是繼續手動補。
