# ADR-0005：接 Google Routes API 取得即時路況，推翻設計架構書 §9

- **狀態**：已採納
- **日期**：2026-08-24
- **相關**：設計架構書 §9、§7.2、§6.2、原則 P6「離線可用」
- **推翻**：設計架構書 §9 的「`driveMinutes` 建議手動填寫實際經驗值，不要接 Directions API」

> **這份 ADR 推翻設計架構書的一條明文決定。** 設計架構書仍是需求的唯一源頭，
> 但 §9 的那條註記已被本文取代，該處需要同步更新。

## 背景

設計架構書 §9 明確反對接路徑規劃 API：

> `driveMinutes` 建議手動填寫實際經驗值，不要接 Directions API。
> 一來省錢，二來自己開過的時間（含找停車位）比 API 準。

這條決定的隱含假設是：**車程是一個穩定的數字**，只要量一次就長期有效，
而 API 量不到的那部分（找車位）正是誤差的主要來源。

使用者於 2026-08-24 指出這個假設是錯的：

> 車程這件事真的很看當下的路況，連假跟一般假日國道路況差異是相當大的，
> 比起有沒有含找車位時間我覺得來得更重要。

這個反駁成立，而且量級差距很明顯：

| 誤差來源 | 典型幅度 |
|----------|----------|
| 連假 vs 一般假日的國道路況 | 20–40 分鐘 |
| 找停車位 | 5–10 分鐘 |

用一個修正 5 分鐘的理由，去放棄修正 40 分鐘的能力，取捨方向是反的。

而且這個誤差直接打在 Stage 1 最硬的那條規則上：
`driveMinutes > maxDriveMinutes → 剔除`。那是一個懸崖，不是漸進的扣分。
連假時系統會照著平日車程放行一堆其實開不到的地點。

## 被考慮的選項

### 選項 A：維持現狀，手填
- 優點：零外部依賴、零成本、P6 離線可用完全不受影響
- 缺點：無法反映當下路況，也就是無法解決使用者提出的實際問題

### 選項 B：全面改用即時 API，移除 `driveMinutes` 欄位
- 優點：永遠準確；建檔少填一個欄位
- 缺點：**直接違反 P6**。沒網路時整個 Stage 1 的車程過濾失效，
  而使用者最需要這個 App 的時刻（人在外面、準備出門）正是訊號最不穩的時候

### 選項 C：即時路況覆蓋，手填值作為基準與離線後備
- 優點：有網路時準確，沒網路時退回基準值，功能不中斷；
  手填值的精度要求下降（只要大概對）
- 缺點：兩個來源要協調，多一層邏輯；仍有外部依賴與帳單帳戶的設定成本

## 決定

選 **C**，由使用者於 2026-08-24 確認。

### 使用的 API

**Google Routes API 的 Compute Route Matrix**，不是已被取代的舊版 Directions API
（Google 於 2025 年 3 月改版）：

```
POST https://routes.googleapis.com/distanceMatrix/v2:computeRouteMatrix
Headers: X-Goog-Api-Key, X-Goog-FieldMask
routingPreference: "TRAFFIC_AWARE"
```

選 Route Matrix 而非 Compute Routes 的理由：我們的形狀正好是「一個起點對多個
目的地」，Route Matrix 一次呼叫就能算完，Compute Routes 要打 N 次。

支援 `departureTime`，所以連假的**預測性**路況也算得進去，
不是只有「此刻」的路況。

### `Place.driveMinutes` 的角色改變

**不刪除這個欄位**，但它的意義從「唯一的車程來源」變成「基準值兼離線後備」：

| 狀態 | 使用的車程 |
|------|-----------|
| 有網路且 API 正常 | Routes API 的即時值 |
| 離線、API 失敗、或超出額度 | `Place.driveMinutes` |

### 成本控制

Compute Route Matrix 按元素計費（起點 × 目的地），Essentials 層每月免費
10,000 個元素。為了不浪費額度，查詢順序刻意設計成兩段：

1. 先用基準 `driveMinutes` 跑完 Stage 1 的**其他**條件（天氣、年齡、推車、時間）
2. 只對存活下來的 5–10 個地點查即時車程
3. 用即時值重跑車程判斷，再進 Stage 2

50 個地點通常只剩 5–10 個，所以一次查詢約 10 個元素。
即使完全不優化、每次查全部 50 個，每月也要 200 次查詢才用完免費額度。

### 對 §8.3 純函式約束的影響：無

`recommend()` **仍然不呼叫網路**。即時車程與天氣走完全相同的路徑：
在呼叫推薦引擎之前取得，透過 `RecommendContext` 傳入。
這條路天氣已經鋪好了，路況只是沿用。

## 後果

- 得到：連假與尖峰時段的車程判斷正確；手填值的精度要求下降
- 放棄：零外部依賴。核心的「今天去哪」路徑現在多一個可能失敗的環節
  （由後備機制降低影響，但不是消除）
- 使用者需要自行申請 Google Cloud 金鑰並綁定帳單帳戶。即使在免費額度內，
  Google 仍要求帳單帳戶才能啟用 API。**這一步無法自動化。**

### 對 §7.2「AI 不得填寫 driveMinutes」的釐清

這條規則**繼續有效，但要精確表述**：

- ❌ **LLM 仍然不得填寫 `driveMinutes`。** §7.2 的理由（「AI 不知道你家在哪」）
  對 LLM 依然成立——它是在猜一個看起來合理的數字。
- ✅ **Routes API 可以填寫。** 它拿到 HomeBase 的實際座標，回傳的是量測值不是猜測。

兩者的差別不是「自動 vs 手動」，是**量測 vs 猜測**。
`fieldSources` 需要一個新的值來表達這個來源（例如 `routes_api`），
與 `ai_suggested` 明確區分。

### 什麼情況下該重新考慮

1. **Google 改價或取消免費額度。** 屆時退回選項 A 的成本很低——
   `driveMinutes` 一直都在，移除即時覆蓋那一層就回到原狀。
2. **實際使用發現即時路況沒有改變任何決定。** 判斷方式：記錄即時值與基準值的差，
   若長期都在 ±5 分鐘內，那這個依賴不值得。
3. 若開始出現「因為 API 掛了而推薦品質下降」的實際經驗，
   要檢討的是後備機制的觸發條件，不是這個決定本身。
