# ADR-0011：推播規格的四項修訂

- **狀態**：已採納
- **日期**：2026-08-25
- **相關**：設計架構書 v1.0 §7.5、§9.1、§9.2、§9.3
- **修訂**：v1.0 §9 的部分條文

## 背景

設計資料模型之前，逐項檢視 §9 的推播規格，使用者提出三個實務問題，
討論後得出四項修訂。這些修訂都源自同一個觀察：

**v1.0 的 P1（零建檔啟動）與 P2（不打開也有用）之間存在結構性張力。**

零建檔意味著地點來自開放資料匯入，也就意味著**大部分推薦的地點，家長沒聽過**。
而對一個沒聽過的地名，推播不可能「自成完整答案」——缺的那塊資訊不在系統裡，
它是「這地方長什麼樣」。

v0.2 沒有這個問題，因為 40–60 個地點都是使用者自己建的。
**v1.0 把建檔成本拿掉的同時，把「認識成本」加了進來，而 §9 沒有處理後者。**

§7.5 只說「未造訪過的地點需標示，且不給精確返家時間」——
那處理的是時間估計的信心度，不是認不認得。

---

## 修訂一：推薦理由依「候選／已驗證」分流

**對熟悉與陌生的地點，家長需要的理由不是同一種。**

| 狀態 | 家長要問的 | 該給的理由 |
|------|-----------|-----------|
| 已驗證 | 為什麼是**今天** | 接得上午睡 · 這個月還沒去過 |
| 候選 | 這是**什麼地方** | 有共融遊戲場，標示適合 2–5 歲 · 停車場大 · 樹蔭多 · 圍起來跑不掉 |

這些資料 §6.2 已經要求要有（設施適齡層、可奔跑空間、安全封閉性、遮蔭、
推車友善、有無冷氣）——那批新欄位本來就是在描述「這是什麼樣的地方」。
目前它們只進評分，不進理由。

**完全在規則模板內完成，不碰 AI 邊界。**

## 修訂二：「沒去」拆成多顆按鈕

§9.3 把採納率定為「長期主力訊號」，但「沒去」一顆按鈕混合了三種完全不同的事：

```
沒去，因為那個地方不吸引我    ← 推薦品質訊號
沒去，因為今天臨時有事        ← 與推薦無關
沒去，因為我們去了別的地方    ← 最有價值，但完全沒被收集
```

改為：

```
［去了］ ［今天沒出門］ ［去了別的地方］ ［看了覺得不適合］
```

- **今天沒出門** → 不影響類別權重。這是生活的問題，不是推薦的問題
- **去了別的地方** → 真訊號；若願意再點一下說去了哪，那是比較性訊號，強度高得多
- **看了覺得不適合** → 處理方式與其他三顆完全不同，見下

### 「看了覺得不適合」是 L2 資料品質最早的修正來源

匯入完成的第一天，所有欄位都是類別先驗值。系統要怎麼發現某個「兒童遊戲場」
其實年久失修、某個「公園」其實只是一塊草地？

規格的答案是「靠造訪紀錄慢慢修正」——但那要等真的去過。
**而「查了照片之後決定不去」發生得比造訪早得多，量也大得多。**
那個判斷比系統手上任何資料都準，目前卻被丟掉。

因此這一顆：
- **不**影響類別權重
- **標記該地點的建檔資料可疑**，降低曝光並列入「待確認」
- 若願意再點一下說哪裡不對（設施不適齡／太遠／看起來很小），
  即為直接的欄位修正建議——對應 §5 核准的 AI 用法 C，只是訊號來得更早

## 修訂三：第二則推播改為雙用途（回饋 + 下午建議）

§11.3 的對照表列了**兩個**出遊窗（例如 24–36m 是「09:00–12:00 或 15:00–17:30」），
但目前設計只用了上午那個。

使用者提議「早上的推播把下午也規劃進去」。**不採用**，理由是：
下午要不要出門取決於上午玩得如何、午睡睡得好不好、家長累不累——
這三件事早上都不知道。放進早上的推播只會稀釋那則推播的清晰度，
而 §9.1 明訂它必須自成完整答案。**一則推播若有一半是猜的，整則的可信度都會被拉低。**

改為併入第二則。時機天然吻合：

```
第二則 = 返家時間 + 1 小時 ≈ 12:10 到家 → 13:10 送出
        小孩正在午睡、家長有空、而下午的出遊窗是 15:00 起
```

此時系統**知道上午的結果**，下午的推薦有依據而非猜測。

附帶效果可能更重要：目前第二則純粹是「幫系統累積資料」，對使用者沒有立即好處，
很容易被滑掉。加上下午建議後，點那三顆按鈕變成有回報的——
**這可能顯著提高回饋率，而回饋率是整個 L3 層的生命線。**

**約束**：§9.2 要求「可整則滑掉」。回饋按鈕在前、下午建議在後，
不回饋也要看得到下午建議，**不得做成「先回饋才給你看」**。

## 修訂四：推播帶「看看這是哪」連結，不帶圖

承認並加速「跳出去查」這個行為，而不是假裝它不存在。

連結開的是地圖服務的**地點頁**（照片與評論），不是導航。
現在的替代路徑是：記住地名 → 切換 App → 打字 → 搜尋 → 找到正確那一筆，四五步。

§9.1 說「不得要求開啟 App 才能理解」——**它禁止的是開「我們的」App。**
跳去看照片是使用者的合理需求，不是設計失敗。

**不帶圖**（使用者決定）：開放資料集通常沒有照片，而地圖服務的照片有授權限制。
這使修訂一、二、四更重要——它們是「沒有照片的情況下，怎麼讓陌生地點變得可判斷」。

## 未修訂的部分

**推播維持主建議 + 備案兩個，不列第三個。** 使用者曾質疑只推一個是否要求過高的精準度。
討論後決定先不動，理由：

1. 它其實不是一個。備案是**不同性質**的（室內、應付天氣突變），不是兩個相似選項
2. Stage 1 已做掉最難的部分；過濾到個位數之後，第一名與第三名的分差通常很小
3. 比較基準不是「完美推薦」而是「憑習慣決定」（§1.3），後者摩擦力為零但品質也未必好
4. **選項數量隨時可改且立刻見效；訊號收髒卻不可回溯。**
   先修訂二，數量等四個週末的實際採納率再說

## 其他已定參數

- 推播時間維持預設 07:30（使用者確認）
- **週日下午一樣推**（使用者確認），不做「週日不推」的特例

## 後果

- §9.1 增加連結；§9.2 增加下午建議；§9.3 的採納率訊號改為多值
- `reasons.ts` 需依地點狀態分流，且與推播文案共用同一組模板（§13.2.9）
- 資料模型需容納：地點狀態（候選／已驗證）、資料可疑標記、多值的採納回饋

### 什麼情況下該重新考慮

1. 四個週末後採納率偏低（例如低於三成），且「看了覺得不適合」佔多數——
   代表問題在建檔資料品質，不是選項數量，此時該檢討先驗值而非加選項
2. 若「今天沒出門」長期佔壓倒多數，代表推播時機或整個形態有問題，
   而不是推薦內容有問題。兩者的處置完全不同，這也是修訂二存在的理由
