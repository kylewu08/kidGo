# ADR-0006：HomeBase 增加 `cwaCountyName` 欄位

- **狀態**：已採納
- **日期**：2026-08-24
- **相關**：設計架構書 §5.4、§9

## 背景

設計架構書 §5.4 的 `HomeBase` 只有一個氣象相關欄位：

```ts
cwaLocationName: string;    // 對應中央氣象署鄉鎮預報地區名，如「板橋區」
```

實際串接 CWA 之後發現這不夠，有兩個原因：

1. **CWA 把鄉鎮預報拆成 22 個縣市各自的資料集**（新北市是 F-D0047-069）。
   光有鄉鎮名稱，決定不了要打哪一個。
2. **鄉鎮名稱不唯一。** 全臺 368 個鄉鎮市區裡，有 8 個名稱橫跨 19 個鄉鎮：
   東區同時存在於新竹市／嘉義市／臺中市／臺南市，
   中正區、中山區、信義區同時存在於基隆市與臺北市。

## 被考慮的選項

### 選項 A：新增 `cwaCountyName` 欄位
- 優點：明確；設定畫面本來就會是「縣市下拉 → 鄉鎮下拉」的兩段式，欄位形狀對應 UI
- 缺點：改 schema

### 選項 B：用既有的 `lat`/`lng` 反查最近的鄉鎮
- 優點：不改 schema。`townships.ts` 已經有 368 個鄉鎮的座標
- 缺點：邊界地區可能選到隔壁鄉鎮。對天氣而言影響極小（隔壁鄉鎮天氣幾乎一樣），
  但多一層推斷，出錯時不容易發現——天氣看起來永遠是「合理的」

### 選項 C：`cwaLocationName` 改存複合字串「新北市/板橋區」
- 優點：欄位數不變
- 缺點：欄位名稱與實際內容不符，接手的人看名稱猜不到裡面是兩段式

## 決定

選 **A**，由使用者於 2026-08-24 確認。

關鍵理由：**設定畫面本來就需要兩段式下拉選單**（縣市 → 鄉鎮），
因為 368 個鄉鎮攤平成一個選單無法使用。既然 UI 一定會分兩段收集，
資料模型就該照實記錄，而不是收完之後合併或丟棄一半。

附帶好處：選完縣市與鄉鎮之後，`lat`/`lng` 可以直接從 `townships.ts` 帶出來，
使用者不需要自己查座標。這也讓 ADR-0005 的 Routes API 有了起點座標。

時機：**現在資料庫是空的，migration 成本等於零。** 這是最便宜的時候。

## 後果

- 得到：氣象資料集的選擇是查表而非推斷；鄉鎮重名不再是問題
- 放棄：`HomeBase` 多一個欄位要填（但由下拉選單提供，不是自由輸入）
- 這是本專案第一次修改設計架構書定義的資料模型，依 `AGENTS.md` 的規定
  經過討論後才動手。設計架構書 §5.4 需要同步更新。

### 什麼情況下該重新考慮

若之後改用別的天氣資料來源（例如直接吃經緯度的 API），這個欄位就失去意義，
屆時應該一併移除而不是留著。
