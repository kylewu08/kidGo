# ADR-0001：資料庫用本地 SQLite，不用 Supabase / Postgres

- **狀態**：已採納
- **日期**：2026-08-23
- **相關**：設計架構書 §8.1、§12.1、原則 P1「個人優先，非平台」、P6「離線可用」

## 背景

KidGo 第一個（也是唯一一個）使用者是開發者本人。v1 明確不做註冊、多租戶與權限系統。
資料量的上限由 P3 界定為 40–60 個地點，加上每週一兩筆 `Visit`——
兩年後的規模大約是幾百列，不是幾百萬列。

同時 P6 要求「離線可用」：帶小孩出門在外網路不穩，核心資料必須本地優先。

## 被考慮的選項

### 選項 A：Supabase（託管 Postgres）
- 優點：多裝置同步免費附贈；未來要開放給其他人用時，帳號系統與 RLS 現成
- 缺點：每次查詢都要網路往返，與 P6 直接衝突；引入一個雲端相依，
  免費層政策改變會影響一個純個人工具；為了 200 列資料維護一套 Postgres 是明顯過度設計

### 選項 B：本地 SQLite + Drizzle
- 優點：零延遲、零成本、天然離線；資料就是一個檔案，備份與匯出都是 `cp`；
  Drizzle 的型別安全與 migration 讓未來換 Postgres 的成本可控
- 缺點：多裝置同步要自己想辦法；部署到 Vercel 這類無狀態平台需要額外處理持久化

## 決定

選 **B：SQLite (better-sqlite3) + Drizzle ORM**。

關鍵理由：**P6 離線可用是產品需求，不是技術偏好。**
使用者真正需要這個 App 的時刻，正是站在戶外、準備出門、訊號不穩的時候。
一個需要往返雲端才能給出建議的決策引擎，在它最該發揮作用的場景裡是壞的。

多裝置同步是一個尚未存在的需求（目前只有一個使用者、一台手機）。
為一個假想的未來需求犧牲一個當下的真實需求，方向反了。

## 後果

- 得到：離線可用、零成本、資料完全自有、備份就是複製一個檔案
- 放棄：多裝置同步。v1 就是單機。
- 已預留的退路（設計架構書 §12）：
  - 選 Drizzle 而非直接寫 SQL，就是為了讓換 Postgres 只需改 driver 與 migration
  - `Place` 從第一天就有 `ownerId` 欄位（v1 全填同一值），未來多使用者不需大改 schema
  - 地點資料可匯出成 JSON，避免被自己的資料庫綁架

### 什麼情況下該重新考慮

1. **出現第二個真實使用者**（不是「未來可能有人要用」，是真的有人在用）——
   此時需要的是完整帳號系統，會連帶觸發 ADR-0001 與整個 §12 的重新評估。
2. **開發者自己開始在兩台裝置上使用並因此感到痛苦**——注意是「感到痛苦」，
   不是「想到可能會痛苦」。
3. 資料量超過數千列，或出現需要跨表複雜查詢的功能。以 v1 的範圍界定，這不會發生。
