# ADR-0021：輸出增加「參考欄」，只收當日條件造成的剔除

- **狀態**：已採納
- **日期**：2026-08-29
- **相關**：設計架構書 v1.0 §7.1、§7.3、§7.5、§13.2.4
- **偏離**：v1.0 §7.3「輸出固定為三項」

## 背景

2026-08-29 用真實資料跑推薦，體感 38°C 那天，**105 個共融遊戲場全部被
`heat` 剔除**（`category-priors.ts` 給 `inclusive_playground` 的
`shadeLevel` 是 1，而 `thresholds.ts` 的 `heatExemptShadeLevelAbove` 是 1）。

使用者檢視後確認**這個剔除是對的**：20 個月的小孩、體感 38°C、無遮蔭的
戶外遊戲場，真的不會去。所以問題不在硬過濾，在於整個類別就這樣消失了，
使用者連「原來附近有這個地方」都不會知道。

## 被考慮的選項

### 選項 A：調整高溫門檻或先驗遮蔭值
- 缺點：§11 明文規定先驗值是「領域判斷，不得自行推導或更改」；
  而調門檻只有兩個方向，一邊讓一般公園也全滅（夏天只剩圖書館），
  另一邊等於取消高溫保護。**而且使用者已經確認剔除本身是對的**——
  調門檻是在修一個沒有壞的東西

### 選項 B：把被剔除的地點降權而非剔除
- 缺點：直接違反 §13.2.4 的精神。高溫對幼兒是安全問題，
  安全問題不該用扣分表達——扣分意味著「夠好的話還是可以去」

### 選項 C：增加一個不參與排序的「參考欄」（採用）

## 決定

選 **C**，由使用者於 2026-08-29 確認。

參考欄**不是第四個推薦**：不參與排序、不進入槽位、
**必須連同剔除理由一起呈現**。它回答的是另一個問題——
「有沒有什麼好地方，只是今天的條件不對？」

### 唯一的約束：出口必須很窄

參考欄是硬過濾的唯一出口。Stage 1 擋掉的東西裡有「緊鄰車道或開放水域」
這種不該以任何形式出現的地方，所以能進來的剔除理由必須是列舉，
判準是**「明天會不會不一樣」**：

| 可進 | 理由 |
|------|------|
| `heat`、`rain` | 天氣，改天就變了 |
| `not_enough_time` | 今天的時間窗不夠，換個時段就行 |

| 不可進 | 理由 |
|--------|------|
| `unsafe_for_toddler` | 緊鄰車道或開放水域。**這種地方不該被看到** |
| `age_out_of_range`、`facility_age_mismatch` | 要等小孩長大，不是「改天」 |
| `stroller_unfriendly`、`parent_effort_too_high` | 這個家庭的固有條件 |
| `drive_too_long` | 距離不會因為換一天而變近 |

挑選規則：優先挑三個槽位沒用到的類別（同類別的沒有增加資訊），
同類別內取車程最近的（那是最可能改天真的會去的）。

## 後果

- **得到**：整個類別因當日天氣消失時，使用者仍然知道它存在。
  這對 §7.4 的防同溫層是同向的——被系統性壓低的類別至少還看得到
- **放棄**：§7.3「輸出固定三項」的字面。實際上是三項推薦加一項說明，
  兩者在呈現上必須明確區分
- **風險**：這是硬過濾唯一的出口。`TRANSIENT_REJECTIONS` 每長一項，
  出口就寬一分。有一個測試守著它維持三項
- **何時重新考慮**：若使用者開始把參考欄當成推薦來用
  （例如回饋顯示他真的在 38°C 去了那個遊戲場），
  代表呈現方式讓剔除理由不夠顯眼，該改的是呈現而不是取消這個欄位
