# ADR-0007：多個核心 `Place` 欄位未進入評分

- **狀態**：**提議中**（尚未決定，待 Phase 1 真實使用後再定）
- **日期**：2026-08-24
- **相關**：設計架構書 §5.2、§6.3

> **這份 ADR 記錄的是一個尚未解決的問題，不是一個決定。**
> 寫下來的理由：它是在實作完 Stage 1 + 2 之後才浮現的，
> 而那個時間點距離「有足夠資料可以判斷」還有好幾週。不記下來一定會忘。

## 問題

實作 §6.3 的六個評分因子之後，稽核 `Place` 的每個欄位有沒有真的影響決策，
發現以下欄位**完全沒有進入 `lib/recommend/`**：

| 欄位 | 設計架構書怎麼描述它 |
|------|---------------------|
| `energyBurn` | §5.2 列在「**核心：現有平台查不到的欄位**」底下 |
| `personalRating` | §5.2「主觀」區塊；AI 不得填寫的三個欄位之一 |
| `crowdLevel` | §5.2「實務情報」，分平日與假日 |
| `parking` | §5.2「位置」區塊 |
| `hasWaterPlay` / `hasFoodOnSite` / `quietHours` / `hasNursingSpace` | §5.2 環境條件與實務情報 |
| `costPerFamily` | §5.2「實務情報」 |
| `indoorBackupPlaceIds` | 屬於 Stage 3（§6.4），尚未實作，**不算缺口** |

`hasChangingTable` 只用來產生警示，不影響分數。

**目前的實作是忠於規格的。** §6.3 明確定義了六個因子——作息、年齡、天氣、
新鮮度、車程、歷史——一個沒多一個沒少。缺口在規格本身，不在實作。

## 為什麼這值得討論

`energyBurn` 的落差最明顯。設計架構書把它放在「現有平台查不到的欄位」，
也就是本產品差異化的核心，但它對排序沒有任何影響。同理 `personalRating`——
開發者親自給某個地點打五顆星，排序完全不理會。

一個合理的懷疑是：**§6.3 的六個因子是在思考「什麼時候去」時列出來的，
而 `energyBurn` / `personalRating` 回答的是「去哪裡」。** 兩組問題都重要，
但只有前者被寫進評分公式。

## 可能的方向（都還沒決定）

### A. 維持現狀
六個因子已經涵蓋最重要的決策維度，其餘欄位的用途是**建檔與查閱**，
不是排序。`energyBurn` 讓你在看到推薦時判斷「今天想不想放這麼多電」，
那是人的判斷不是機器的。

### B. 新增因子
例如「放電契合度」（今天想放多少電 vs 地點的 `energyBurn`），
但這需要在 `RecommendContext` 增加一個「今天的意圖」輸入，
而那會改變產品的互動形狀——從「回答我」變成「先問我幾個問題」，
與 P2「答案優先，非清單」的精神有張力。

### C. 只把 `personalRating` 併進歷史成效
`personalRating` 與 `Visit.outcome` 在語意上很接近（都是「這裡好不好」），
可以合併進那 5% 的因子，作為還沒有紀錄時的先驗值。
這個改動最小，而且不需要新增輸入。

## 為什麼現在不決定

設計架構書 §11 的 Phase 1 驗收標準是「連續四個週末，開發者自己真的打開它
並照建議出門」。推薦品質只能靠真實使用判斷，而真實使用需要介面加上
40–60 個真實地點。

在那之前，任何調整都是在對雜訊調參——目前唯一跑過的資料是煙霧測試裡
四個手工捏造的地點。

**決定的時機**：Phase 1 完成、累積若干個週末的實際使用之後。
判斷依據應該是具體的不滿，例如「它一直推薦放電量不夠的地方」，
而不是「感覺少了什麼」。

## 附帶的觀察

若最後選 A（維持現狀），那 §5.2 的欄位清單應該加註哪些欄位進評分、
哪些只供查閱。目前讀者會合理地假設「核心欄位」都有進決策，而事實不是。
