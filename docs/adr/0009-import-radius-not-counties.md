# ADR-0009：匯入全臺資料，但只對住家直線半徑內的地點計算基準車程

- **狀態**：已採納
- **日期**：2026-08-25
- **相關**：設計架構書 v1.0 §P4、§10.1、§10.3
- **偏離**：v1.0 §10.1「匯入範圍限住家縣市與鄰近縣市」的字面寫法

## 背景

v1.0 §P4 定義窄而深為「匯入範圍限住家縣市與鄰近縣市」。
實作前檢視這個界定，發現**縣市邊界與車程幾乎無關**。以板橋為起點：

| 目的地 | 直線距離 | 行政關係 |
|--------|----------|----------|
| 桃園龜山 | 約 13 km | 鄰縣市 |
| 新北萬里 | 約 28 km | **同縣市** |
| 宜蘭市 | 約 41 km | 鄰縣市（翻山） |
| 臺中 | 約 123 km | 不鄰接 |

依縣市匯入會把萬里判為近、龜山判為遠，兩個都錯。

同時釐清了一件事：**真正的成本不是儲存，是基準車程的 API 額度。**
政府開放資料下載後就是本地檔案，全臺收下來不花錢也不影響查詢速度。
但 §10.3 的基準車程計算每月僅 10,000 次免費，全臺可能上萬筆地點，
一次匯入就會燒光額度，而且大半花在三百公里外的地方。

## 被考慮的選項

### 選項 A：照字面，只匯入住家縣市與鄰近縣市
- 優點：實作最簡單；符合規格字面
- 缺點：誤判如上；需要維護一份「哪些縣市算鄰近」的清單，
  而那份清單本身就是一組沒有依據的判斷

### 選項 B：全臺匯入，用直線半徑決定要對誰算基準車程
- 優點：判斷依據是距離本身而不是行政劃分；
  改住家或調高車程上限時只需增量補算；
  Phase 3 的過夜規劃用同一份資料換一個半徑即可
- 缺點：偏離規格字面，需要本文說明

### 選項 C：先用縣市粗篩，再用半徑細篩
- 優點：資料量更小
- 缺點：多一層複雜度，換到的好處很小——全臺資料離線儲存本來就不花錢

## 決定

選 **B**，由使用者於 2026-08-25 確認。使用者原話：
「我不能涵蓋全台然後依照使用者輸入住家地點之後，再去搜尋附近縣市的資料嗎？」

分兩層：

```
匯入（免費、離線）      全臺資料集照收
基準車程（消耗額度）    只算住家直線半徑內的，其餘留空並標記「距離過遠」
```

### 半徑怎麼定

由使用者的車程上限推導，而不是寫死：45 分鐘走高速約 60 km 路程，
直線距離約為路程的 0.7–0.8 倍即 45–55 km，取約 1.5 倍安全係數 ≈ **75 km**。

驗證：宜蘭（41 km）落在範圍內，臺中（123 km）落在範圍外。
兩者都符合「當日出遊」的直覺。

**窄而深的精神仍然守住：窄的是計算車程的範圍，不是收資料的範圍。**

## 後果

- 得到：不需維護「鄰近縣市」清單；邊界地帶判斷正確；改設定時可增量補算
- 得到：Phase 3 過夜規劃可直接沿用同一份資料，只需放大半徑
- 放棄：規格字面的一致性。§10.1 的該句應視為被本文取代
- 未解決：v1.0 §10.3 自己標記的「待確認事項」——Google Maps Platform 服務條款
  對路徑／ETA 結果的長期儲存有限制。半徑做法減少了儲存筆數但沒有回答合規問題。
  **實作匯入器之前必須先確認。**

### 什麼情況下該重新考慮

1. 若全臺資料集的總量大到影響匯入時間或本地儲存（判斷方式是實際下載後量測，
   不是憑感覺），再退回選項 C 的兩層篩選
2. 若上述 Google ToS 的確認結果是「基準車程不得長期儲存」，
   則整個基準車程的概念要重新設計，本文的半徑做法也要跟著調整
