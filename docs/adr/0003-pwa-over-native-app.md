# ADR-0003：做 PWA，不做原生 App

- **狀態**：已採納
- **日期**：2026-08-23
- **相關**：設計架構書 §8.1、原則 P1「個人優先，非平台」、P6「離線可用」

## 背景

這是一個手機優先的工具——使用情境是週末早上站在家裡想「今天帶小孩去哪」，
或是在車上臨時改主意。桌機幾乎不會用到。設計架構書 §10.1 的畫面規格
明確要求「手機單手可操作」、斷點以 375px 為基準。

手機優先通常意味著原生 App。

## 被考慮的選項

### 選項 A：原生 App（Swift / Kotlin，或 React Native / Expo）
- 優點：最好的手機體驗；推播通知可靠（§10.3 提到「離開時提醒記錄這次」是關鍵留存機制）；
  真正的離線能力
- 缺點：iOS + Android 雙平台成本；上架審查流程；為了一個自己用的工具付 Apple 開發者年費；
  每次改動都要重新送審才能用到

### 選項 B：Next.js PWA，加到主畫面
- 優點：單一 repo 涵蓋前後端；改完 push 就生效，沒有審查；
  Service Worker 可滿足 P6 的離線快取；零上架成本
- 缺點：iOS 的 PWA 推播支援歷來不穩；體驗略遜於原生

## 決定

選 **B：PWA**。

關鍵理由：**P1 說這是個人工具不是平台，那麼上架流程帶來的一切成本都是純損失。**
沒有 App Store 曝光需求、沒有版本管理需求、沒有其他使用者要等更新——
送審機制在這個專案裡只有壞處。

雙平台成本則是第二個理由：開發者只有一支手機，為了假想的另一個平台先付出成本，
違反 P3「窄而深，非廣而淺」的精神。

## 後果

- 得到：改完即用、單一程式碼庫、零上架與年費成本
- 放棄：可靠的推播。§10.3 的「離開時提醒記錄這次」在 PWA 上不保證可用，
  Phase 2 實作出遊紀錄時需要退而求其次（例如開啟 App 時的提示，或行事曆整合）。
  **這是這個決定最實質的代價，實作 Phase 2 時不要假裝它不存在。**
- 放棄：部分原生能力（背景定位、精細的觸覺回饋）。目前的功能規格都用不到。

### 什麼情況下該重新考慮

1. **推播被證明是留存的關鍵，而 PWA 做不到。** 判斷方式是實際做完 Phase 2 之後，
   觀察自己有沒有真的回填出遊紀錄——如果因為沒有提醒就不填，那 L3 這層資料永遠累積不起來，
   此時推播就從「錦上添花」變成「產品成立的前提」，值得重新評估。
2. 產品開放給真實的其他使用者（同時觸發 ADR-0001 的重新評估）。
