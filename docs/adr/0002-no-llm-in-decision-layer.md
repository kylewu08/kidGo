# ADR-0002：決策層禁用 LLM，推薦排序由確定性純函式產生

- **狀態**：已採納
- **日期**：2026-08-23
- **相關**：設計架構書 §3、§6、§8.3、原則 P7「決策邏輯必須可讀可測」

> **這是本專案最重要的一份 ADR。**
> 它違反 2026 年的直覺（「有 LLM 為什麼還要自己寫評分函式？」），
> 如果不寫下來，未來一定會有人——包括 AI 協作工具——好意地把它「優化」掉。

## 背景

推薦邏輯的輸入是「天氣 × 小孩作息階段 × 車程上限 × 現在幾點」，
輸出是一到三個具體地點加上理由。這個形狀看起來非常適合直接丟給 LLM 處理，
而且那樣做可以在一個下午內完成，不需要 `filters.ts` / `scoring.ts` / `diversity.ts`
這一整套程式碼。

## 被考慮的選項

### 選項 A：把地點清單與情境丟進 prompt，讓 LLM 排序並產生理由
- 優點：實作成本極低；理由天然是人話；新增判斷規則只要改 prompt
- 缺點：見下方「決定」

### 選項 B：確定性評分函式（Stage 1 硬性過濾 + Stage 2 加權評分 + Stage 3 多樣性調整），
LLM 只在資料層（建檔）與呈現層（潤飾句子）出現
- 優點：可重現、可測試、可除錯、零邊際成本
- 缺點：規則要自己寫；理由是模板產生的，語氣較硬

## 決定

選 **B**。四個理由，其中第二個是決定性的：

### 1. 不可重現就無法調參
同樣條件在不同時間得到不同答案，就無法回答「為什麼今天的建議變了」。
而**調權重是這個產品的長期核心工作**（P7 說評分規則是本產品最有價值的資產）。
一個無法穩定重現的系統，你連自己有沒有把它調好都不知道。

### 2. 幻覺的代價不對稱
「推車可以進、四點才關門」這種話答錯一次，代價是**帶著一歲半的小孩白跑一趟**。
這不是重跑一次就能補救的錯誤——那個下午已經沒了，小孩已經在車上崩潰了。

一般 LLM 應用可以接受「偶爾錯，使用者會發現」；這個產品不行。
使用者發現錯誤的時候，人已經在現場了。

### 3. `Visit` 紀錄無法回饋進黑箱
設計架構書 §2 的核心心智模型是三層疊加，其中 L3（實際紀錄）需要一個
**可修改的評分函式**才能發揮作用。把歷史紀錄塞進 prompt 是黑箱——
你無法驗證它到底有沒有被納入考量，也無法把權重刻意壓在 5%。

### 4. 護城河
若本產品只是「AI 搜尋並推薦」，使用者今天用 ChatGPT 就能免費達成，產品沒有存在必要。
聊天介面給不了的是持久狀態、驗證過的在地事實、個人歷史——
**這三件事的價值來自資料的持久化與判斷的一致性，不是來自模型的生成能力。**

## 後果

- 得到：可單元測試的決策邏輯、零查詢成本、可解釋的排序、能被人類接手維護的規則
- 放棄：實作速度。Stage 1+2 加上測試是 Phase 1 最大的一塊工作。
- 放棄：規則的表達彈性。LLM 能處理「今天有點悶但不至於下雨」這種模糊情境，
  門檻值不行。這是刻意接受的代價。

### 這條界線的具體執行

- `lib/ai/` 與 `lib/recommend/` **互不 import**，由 `eslint.config.mjs` 的
  `no-restricted-imports` 強制。違反會 lint 失敗，不是靠自律。
- `recommend()` 是純函式：無副作用、不讀 DB、不呼叫網路（§8.3）。
- `Recommendation.reasons` 由 `lib/recommend/reasons.ts` 的規則模板產生。
  呈現層的 LLM **可以潤飾句子，不得改變語意，不得新增規則未產生的理由**。

### 什麼情況下該重新考慮

**基本上沒有。** 但如果真的要重新考慮，前提至少是：

1. 有一組足夠大的 `Visit` 紀錄（數百筆）可以拿來**離線評測**——
   也就是能證明 LLM 排序比現行函式更準，而不是「感覺比較聰明」。
2. 重新考慮的對象是 Stage 2 的**權重**，不是 Stage 1 的硬性過濾。
   Stage 1 編碼的是育兒常識（雨天不去純戶外、午睡前回不了家就不去），
   那些是事實判斷，永遠不該交給機率模型。
