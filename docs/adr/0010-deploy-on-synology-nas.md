# ADR-0010：部署在自有的 Synology NAS，SQLite 保留

- **狀態**：已採納
- **日期**：2026-08-25
- **相關**：[ADR-0001](0001-sqlite-over-cloud-db.md)（解決其未決的部署問題）、
  設計架構書 v1.0 §9（推播）、§9.4（iOS 平台限制）

## 背景

ADR-0001 選了本地 SQLite，理由是 P6 離線可用與零成本。當時**沒有回答部署問題**——
因為 v0.2 的形態是「打開 App 看首頁」，跑在開發者自己的電腦上就夠用。

v1.0 §1.3 把主要形態改成**週末早晨的推播**。這使部署從「早晚要處理」變成
「不處理就沒有產品」：

1. 推播必須由伺服器在**無使用者互動**的情況下於固定時刻送出，
   代表需要一台常開的機器與排程器
2. Web Push 需要 HTTPS（Service Worker 只在安全內容中運作），
   代表需要有效憑證與固定網址
3. §9.4：iOS 的 Web Push 僅在 PWA 被加入主畫面後可用，
   而加入主畫面需要一個穩定的來源網址

## 被考慮的選項

### 選項 A：Vercel 或 Google Cloud Run
- 優點：部署最簡單，憑證自動
- 缺點：**兩者都是無狀態的，沒有持久磁碟。** SQLite 檔案每次部署即消失。
  選它等於同時推翻 ADR-0001，被迫改用 Postgres 或 Cloud SQL，
  而那個改動本身沒有任何產品上的理由——純粹是被部署平台逼的

### 選項 B：Fly.io（或 Railway）
- 優點：有持久 volume，SQLite 可原封保留；憑證自動處理
- 缺點：多一個外部依賴；免費額度政策會變；資料離開自己手上

### 選項 C：自有的 Synology NAS
- 優點：持久磁碟讓 **SQLite 完全不用動**（ADR-0001 保持成立）；
  零邊際成本；資料完全自有，呼應 §1.4 個人優先；沒有冷啟動；
  Synology 內建 DDNS、Let's Encrypt 自動憑證、Container Manager、排程任務——
  推播需要的三件事都有現成介面
- 缺點：可用性由自己負責，NAS 掛掉週六早上就沒有推播；
  若對外網路是電信商 CGNAT 則 DDNS 穿不出去

## 決定

選 **C：Synology NAS**，由使用者於 2026-08-25 確認。

關鍵理由：**它是唯一不需要為了部署而改變資料層的選項。**
選 A 會逼出一次沒有產品理由的資料庫遷移，而那正是 ADR-0001 想避免的事。

**NAS 與住家不在同一個網域不是問題。** 這台伺服器不需要在家裡——
HomeBase 只是資料庫裡的一組座標，與主機的實體位置無關。
伺服器只需要：能連外網、有 HTTPS、常開。

### 需要建立的三件事

| 項目 | Synology 的對應 |
|------|----------------|
| 固定網址 | 內建 DDNS |
| HTTPS 憑證 | 內建 Let's Encrypt 自動更新 |
| 排程（週六日 07:30） | 控制台的排程任務，或容器內的排程器 |

應用本身以 Container Manager（Docker）執行，SQLite 檔案放在掛載的磁碟區。

## 後果

- 得到：ADR-0001 完整保留，不需要資料庫遷移
- 得到：零月費；資料不離開自己的硬體
- 放棄：託管平台的可用性保證。NAS 停機時當週推播不會送出。
  **這是個人工具，可以接受**——但要意識到它是一個真實的失敗模式
- 新增責任：憑證到期、Docker image 更新、NAS 韌體更新都要自己顧

### 已知風險

**CGNAT**：若電信商未提供真實對外 IP，DDNS 無法穿透。
此時的解法是 Cloudflare Tunnel（不需要對外 IP），複雜度上升但仍可行。
**動工部署前應先確認這一點**，不要等到憑證都設好了才發現連不進來。

### 什麼情況下該重新考慮

1. 連續兩個週末因為 NAS 不可用而漏掉推播——那代表可用性的代價是真的，
   此時改用 Fly.io（選項 B）仍可保留 SQLite
2. 產品開放給真實的其他使用者（同時觸發 ADR-0001 與 ADR-0003 的重新評估）
