## 1\. 產品目標

### 1.1 要解決的問題

帶幼兒出遊時，家長每個週末都要在腦中做一次多變數計算：小孩現在的作息階段、今天的天氣、可接受的車程、那個地方適不適合這個年紀、去了自己會不會累垮。現有工具沒有一個同時處理這些變數——旅遊 App 假設你已經知道要去哪，只幫你排時間；親子景點懶人包是靜態文章，無法依當下條件篩選。

### 1.2 產品定義

**這是一個決策引擎，不是景點資料庫。**

輸入當下條件，輸出一到三個具體答案，而非讓使用者從清單中自行篩選。收錄地點的數量永遠不是成功指標；判斷的準確度才是。

### 1.3 形態定義

**主要介面是週末早晨的一則推播，不是一個等待被開啟的 App。**

週六早晨的真實替代方案不是「打開別的 App」，而是「憑習慣決定」——後者摩擦力為零。任何需要主動開啟的工具都在與零摩擦競爭。App 的角色是設定介面與回饋介面。

### 1.4 使用者

第一個且唯一的使用者是開發者本人。不做註冊、社群、UGC、業者後台。這消除了冷啟動問題，也讓所有設計可以針對單一真實家庭最佳化。

## 3\. 決策的三個來源

推薦結果由三層疊加產生。**它們具備的時間點不同，這是產品第一天就能用的原因。**

| 層 | 來源 | 何時具備 | 角色 |
| :---- | :---- | :---- | :---- |
| L1 判斷力 | 育兒常識（下雨不去戶外、午睡前要到家） | 第一天 | 硬性過濾：決定「哪些不可能」 |
| L2 靜態事實 | 開放資料 \+ 類別先驗值 | 匯入後即有 | 加權評分：決定「哪些可能」 |
| L3 實際紀錄 | 造訪回饋累積 | 持續累積 | 微調（僅 5%）：決定「哪些真的行」 |

**L3 權重刻意壓低。** 少量紀錄算不出可信平均值，過度加權只會產生雜訊。紀錄真正的價值不是自動調整排序，而是**讓使用者發現靜態欄位填錯了**——例如某地點連續三次「停留時間比較短」，代表預估時長需下修。因此地點詳情頁必須提供「建檔值 vs 實際紀錄」的對照視圖，讓這種落差肉眼可見。

## 5\. AI 的使用判準

決定 AI 能否介入的不是「在哪一層」，而是**輸出的性質**。

> **AI 的輸出必須是「對設定的提議」或「對輸入的轉譯」，永遠不能是「對排序的決定」。**

| 輸出性質 | 例子 | 允許 | 理由 |
| :---- | :---- | :---- | :---- |
| 對輸入的轉譯 | 「今天外婆一起去」→ 放寬家長負擔上限 | ✅ | 引擎仍為純函式，僅參數不同 |
| 對設定的提議 | 「建議調降家長負擔上限」→ 待核可 | ✅ | 人為最終決定者，可追溯可撤回 |
| 對排序的決定 | 「把這 8 個候選重排」 | ❌ | 不可重現、無法除錯、紀錄無法回饋 |

**為什麼排序禁用 AI**：不可重現（同條件不同答案，無法調參）、幻覺代價不對稱（「推車可進」答錯一次＝帶小孩白跑）、紀錄無法回饋（黑箱累積不出東西）、每次查詢皆有成本。且 Stage 1 已完成困難的工作，剩下的排序恰是規則最擅長的部分。

### 核准的 AI 用法

| 用法 | 性質 | 階段 |
| :---- | :---- | :---- |
| A. 一次性情境轉譯（§8） | 轉譯輸入 | Phase 1 |
| B. 離線模式偵測：月讀紀錄提出假設，待核可 | 提議設定 | Phase 2 |
| C. 自由筆記結構化：轉為欄位修正建議，待核可 | 提議設定 | Phase 2 |
| D. 新地點建檔草稿：僅適用未造訪過的地點 | 提議設定 | Phase 2 |

**B、C、D 皆不在決策路徑上，執行失敗不影響推薦運作。**

### 護城河檢查

若本產品僅是「AI 搜尋並推薦」，使用者今天即可用通用聊天工具免費達成。三件聊天介面給不了的事，必須是本產品的核心：

1. **持久狀態** — 不需每次重述小孩月齡與作息，且隨月齡自動演進  
2. **驗證過的在地事實** — 親自確認的資訊，非模型推測  
3. **個人歷史** — 「上次 18 個月來撐了兩小時」，任何模型都生不出來

## 6\. 領域語彙

以下是本產品的核心概念。**名稱與意義需在實作中保持一致**，但資料結構由實作者設計。

### 6.1 小孩

| 概念 | 意義 | 取值 |
| :---- | :---- | :---- |
| 作息階段 | 由月齡推導，可手動覆寫 | 兩段午睡 / 單段午睡 / 過渡期 / 已無午睡 |
| 午睡窗 | 影響可用時間窗計算 | 起訖時刻 |
| 行動力 | 影響推車需求與安全考量 | 需抱 / 推車 / 能走但續航短 / 能自行走完 |

作息階段與行動力是整個推薦邏輯的支點，也是本產品相對於一般旅遊 App 的結構性優勢——**它們每 3–6 個月改變一次，推薦結果必須跟著變，這本身構成回訪理由。**

### 6.2 地點

**欄位設計原則：只記錄地圖服務與現有懶人包查不到的東西。**

| 概念 | 意義 | 取值 |
| :---- | :---- | :---- |
| 放電強度 | 消耗小孩體力的程度 | 1–5 |
| 預估停留時長 | 實際能撐多久，非官方建議時間 | 分鐘 |
| 適合時段 | 對應作息窗 | 清晨 / 上午 / 午睡後 / 傍晚 |
| **設施適齡層** | 現場遊具實際適用的年齡層；空值代表無遊具設施 | 嬰兒 / 學步兒 / 學齡前 / 學齡 |
| **可奔跑空間** | 能否自由跑動 | 0–3 |
| **安全封閉性** | 3＝跑不掉；0＝鄰接車道或開放水域 | 0–3 |
| **家長負擔** | 家長的體力消耗 | 1–5 |
| 有無冷氣 | 夏季關鍵 | 是 / 否 |
| 室內外類型 | 決定雨天與酷暑可用性 | 室內 / 戶外 / 混合 / 有遮蔽戶外 |
| 遮蔭程度 | 對高溫的補償 | 0–3 |
| 推車友善 | — | 是 / 否 |
| 基準車程 | 匯入時自動計算，僅供粗篩，不呈現給使用者 | 分鐘 |
| 是否走國道 | 決定是否受連假影響 | 是 / 否 |
| 找車位時間 | 加在車程估算上 | 分鐘 |
| 狀態 | 候選（未造訪）/ 已驗證（有造訪紀錄） | — |
| 欄位來源 | 每個欄位各自標記 | 類別先驗 / AI 建議 / 手動 / 紀錄修正 |

**為什麼需要「可奔跑空間」與「家長負擔」**：以下三個地點在只有「放電強度」的模型中無法區分，但對幼兒家長是完全不同的選擇。

|  | 美術館 | 大型兒童樂園 | 沙灘 |
| :---- | :---- | :---- | :---- |
| 設施適齡層 | 無設施 | 學齡前、學齡 | 無設施 |
| 可奔跑空間 | 3 | 1 | 3 |
| 家長負擔 | **1** | 3 | **5** |
| 有無冷氣 | 是 | 否 | 否 |
| 安全封閉性 | 3 | 3 | **1** |

美術館雖無遊具、放電強度低，但對 20 個月幼兒是好選擇：可跑、家長不累、有冷氣、跑不掉。大型兒童樂園則因設施不適齡且無可跑空間，**應在硬過濾階段即被剔除**。

**家長負擔是決策中被長期忽略的變數**：決定要不要去的是家長，「小孩玩得開心但家長累垮」與「兩者皆可」是不同的結果，而任何懶人包都不會記錄這件事。

**欄位來源必須逐欄位追蹤**：類別先驗值的可信度低於親身驗證。UI 需能區分「系統猜的」與「我確認過的」，否則錯誤資料混入後無法追查。

### 6.3 家庭偏好

小孩約束決定「哪些不可能」，家庭偏好決定「哪些你們真的會去」。

| 概念 | 意義 | 來源 |
| :---- | :---- | :---- |
| 戶外傾向 | 偏室內 ←→ 偏戶外 | 初始三題 |
| 家長負擔上限 | 可接受的上限 | 初始三題 |
| 是否需含用餐 | — | 初始三題 |
| 類別權重 | 各類別的相對偏好 | 回饋累積學習 |
| 手動覆寫 | 優先於學習值，且不再被自動調整 | 使用者設定 |

**學習訊號**：採納建議（權重↑）、跳過建議（權重↓，幅度小於採納）、回饋「順利」（權重↑↑）。跳過的降權幅度刻意較小，因為「沒去」的原因多且雜訊高。

**權重必須可見且可改（硬性要求）**：UI 需顯示學習結果與依據（例如「戶外公園 \+35%，依你最近 12 次選擇」）並提供調整與重設。理由與 §5 一致——你必須能在半年後說「這條學錯了」並改掉它。樣本數不足時（建議少於 8 筆）不套用學習權重。

### 6.4 造訪紀錄

**唯二必填：停留時間感受（比較短／差不多／比較久）、過程結果（順利／普通／崩潰）。** 兩者皆由推播上的按鈕產生。

其餘（實際到離時間、實際車程、詳細筆記）一律選填，且 Phase 1 不主動收集。理由見 §9.2。

紀錄必須保存**當次的小孩月齡快照**——兩年後回顧「18 個月時的結果」才有意義，用出生日期反推會失去情境。若當次套用過一次性情境覆寫，該覆寫內容亦須一併保存，否則日後會誤讀（例：「因外婆同行才去沙灘」不應被解讀為「沙灘一直都適合我們家」）。

紀錄為**永不刪除**的資產。

## 7\. 推薦流程

三段式：硬性過濾 → 加權評分 → 多樣性調整。

### 7.1 Stage 1：硬性過濾

不符合者直接剔除，不進入評分。此階段用掉 L1 判斷力，通常能將數百筆縮減至個位數。

**車程採兩段式估算，避免對全部地點呼叫路況 API：**

- **粗篩**（零 API 呼叫，全部地點）：以基準車程乘上日型係數，超過上限的剔除。門檻放寬約 20%，避免粗估誤差誤殺  
- **精算**（僅對存活的前 8 名）：查詢即時路況，去程與回程分別計算

**過濾條件：**

| 條件 | 判定 |
| :---- | :---- |
| 車程 | 超過使用者設定上限 |
| 時間 | 可用時間不足以完成「去程＋停留＋回程」 |
| 降雨 | 降雨機率高於 60% 且為純戶外 |
| 高溫 | 體感溫度高於 33°C 且為純戶外且遮蔭不足 |
| 月齡 | 不在地點適用年齡範圍內 |
| 推車 | 需推車但地點不友善 |
| **適齡** | **有遊具設施但不含小孩年齡層，且無可奔跑空間可替代** |
| **家長負擔** | **超過偏好設定的上限** |
| **安全** | **幼兒階段（需抱／續航短）且安全封閉性過低** |
| 需預約 | 標記警示，不剔除 |

**適齡必須是硬過濾，不是扣分項。** 家長不會「去了才發現不適合」，而是看到現場只有大型遊具就事前排除。

**回程必須獨立計算**，不可假設等於去程。早上出發與下午返程是不同的路況，而「能否在午睡前返家」正是依賴回程。

### 7.2 Stage 2：加權評分

| 因子 | 權重 | 說明 |
| :---- | :---- | :---- |
| 作息契合度 | 25% | 現在時段是否適合；能否在午睡前完成或午睡後開始 |
| 年齡契合度 | 20% | 落在最適齡區間給滿分；可奔跑空間可補償無適齡設施 |
| 天氣適配度 | 15% | 晴天戶外加分；遮蔭對高溫的補償 |
| **家庭偏好** | **15%** | 類別權重與戶外傾向；見 §7.4 的抑制規則 |
| 新鮮度 | 10% | 距上次造訪越久越高；近期造訪大幅降權 |
| 車程成本 | 10% | 非線性，短程差異不大，超過門檻後急降；壅塞另計懲罰 |
| 歷史成效 | 5% | 過往回饋；「崩潰」為負向 |

**壅塞懲罰**：塞車的成本不只是時間。在國道塞 40 分鐘與在一般道路開 40 分鐘，對小孩是完全不同的事——前者伴隨額外的車上崩潰風險。因此對「實際車程／基準車程」的比值需**超線性**懲罰，且僅在明顯壅塞後才開始生效。

**多小孩情境**：對每個小孩獨立算分，取**最低分**而非平均。理由：只要有一個不適合，整趟就毀了。這是刻意的保守設計。

### 7.3 Stage 3：多樣性

輸出固定為三項：

1. **主建議** — 綜合分數最高  
2. **備案** — 至少一個室內選項，供天氣突變  
3. **探索槽** — 見 §7.4

前三名不得為同一類別。

### 7.4 防同溫層機制

**問題**：偏好學習會持續壓低不偏好的類別。若家庭偏好戶外，室內選項將長期被降權、鮮少造訪、資料停留在類別先驗值而未被修正。**於是在下雨天——正是最需要室內選項的時刻——系統手上只剩品質最差、從未驗證的牌。** 偏好學習的失效點，恰好落在產品最該發揮價值的情境。

**防線一：偏好權重在受限情境下歸零。** 當降雨機率高、體感溫度過高、或硬過濾後存活數量已很少時，偏好權重設為零，所有存活選項以原始分數競爭。**偏好只能調整排序，永遠不能覆蓋硬過濾。**

**防線二：探索槽優先分配給偏好之外的類別**，而非單純選最新鮮的地點。

**已知代價（設計上接受）**：探索槽偶爾會推出使用者明知不會去的地點，短期看似推薦品質下降。**這是保險費，不是缺陷**——它讓系統在雨天仍有經過驗證的室內選項可用。實作時不得為了「提升推薦精準度」而移除探索槽；若長期未被採納，可降低出現頻率，但不得完全關閉。

### 7.5 輸出要求

- 推薦理由必須是**人話**，不顯示分數  
- 理由由規則模板產生，須與評分結果一致；AI 不得新增規則未產生的理由  
- 未造訪過的地點需標示，且不給精確返家時間（其停留時長僅為估計值）

### 7.6 引擎的架構約束

**推薦引擎必須是純函式**：無副作用、不讀資料庫、不呼叫網路、不依賴 UI 狀態。

理由有二：其一，調整權重是長期持續的工作，沒有單元測試會越調越亂；其二，**推播需在伺服器端於無使用者互動的情況下執行**，任何對 UI 狀態的依賴都會使此形態無法成立。

外部資料（天氣、路況、紀錄）由呼叫端取得後傳入。

## 8\. 一次性情境輸入

### 問題

模型只描述常態：月齡、平常作息、家庭偏好。但真實週末充滿一次性變數——外婆同行、昨晚沒睡好、剛接種疫苗、下午須返家收件。**這些無法列舉成欄位，因為長尾無限**，但每個月都會發生。

### 設計

推播落地頁提供一個選填的自由輸入框。AI 將自然語言轉譯為**對推薦條件的覆寫**，可覆寫的範圍限於：家長負擔上限、可用時間窗、車程上限、是否避開人多、放電強度上限。

### 硬性規則

1. 僅能覆寫既有的推薦條件，**不得新增評分因子、不得直接影響排序**  
2. 覆寫內容必須明示於 UI，且可逐項取消  
3. **僅對本次有效**，不寫入家庭偏好，不影響長期學習  
4. 原始輸入與轉譯說明須存入該次造訪紀錄  
5. 無法解析時，回覆「無法理解，將以一般條件推薦」並照常執行，**不得中斷流程**  
6. AI 輸出須經型別與範圍驗證後才可使用；超出允許範圍的值一律丟棄

這是本產品中 AI 唯一進入即時路徑的位置，但它處理的是**輸入**，決策仍完全由規則產生。

## 9\. 推播規格

### 9.1 第一則：當日建議

**排程**：週六、週日早晨（預設 07:30，需可設定）。**時間點必須早於決策發生**——太晚送出，使用者已經自行決定了。

**執行流程**：取得天氣 → 判定日型 → 計算可用時間窗 → 執行推薦 → 精算前 8 名車程 → 生成文案 → 送出。

**內容要求**：

- **整則必須自成完整答案，不得要求開啟 App 才能理解**  
- 純文字，可一鍵轉傳給另一半（決策通常是雙人的）  
- 主建議一個、備案一個，**不列第三個**（選項越多越難決定）  
- 出發時間須具體到分鐘

**「今天不要出門」是合法輸出**：若硬過濾後無存活地點，推播不得沉默，也不得降低標準硬推。「今天大雨、體感 34°C，建議在家」是有價值的輸出——它省下了糾結的成本。此路徑需獨立的文案模板。

### 9.2 第二則：回饋

**時間點**：當日建議的返家時間 \+ 1 小時（**非傍晚**）。此時小孩多半在午睡、家長有空、記憶仍新。傍晚才問會遺失細節，且錯過家長真正有空的窗口。

若當日未推播建議、或使用者未表示前往，則不送出。

**內容：三次點擊完成，無數字輸入、無文字輸入、可整則滑掉。**

- 停留時間：比較短 / 差不多 / 比較久  
- 過程：順利 / 普通 / 崩潰  
- （選填）加註記

**資料如何取得而不增加負擔**：

| 需要的資料 | 方式 |
| :---- | :---- |
| 停留時長修正 | 由「比較短／久」相對調整，不需知道確切分鐘數 |
| 結果與崩潰 | 由過程按鈕推導 |
| 到離時間 | 取當日推播的建議值，不要求使用者提供 |
| 實際車程 | Phase 1 不收集 |

**實作禁令**：第二則推播不得改為「開啟 App 以記錄」的導流通知。若使用者必須開啟 App 才能回饋，此設計即失效。

### 9.3 回饋的三層強度

| 層級 | 操作 | 取得 |
| :---- | :---- | :---- |
| 最輕 | 第一則推播上的「去了 / 沒去」 | 採納率——**長期主力訊號** |
| 標準 | 第二則推播的三次點擊 | 時長修正、結果 |
| 完整 | 主動開啟 App 填寫 | 詳細資料 |

**系統不依賴使用者的勤勞。** 即使標準層每次都被跳過，偏好學習仍能運作，只是地點欄位修正得較慢。完整層永不主動要求。

**若使用者連續多次「沒去」**，代表推薦品質有問題，應在 App 內顯示提示，而非持續推播。

### 9.4 平台限制（必讀）

**iOS 的 Web Push 僅在 PWA 被加入主畫面後可用**（iOS 16.4 起）。這是平台限制，非實作問題。

首次設定流程**必須**引導使用者完成此步驟，並在未完成前明確告知推播無法運作。若略過，整個產品形態對 iPhone 使用者失效。

## 10\. 資料來源

### 10.1 地點種子（Phase 1，自動匯入）

**使用者不手動建立任何地點。** 初始輸入僅住家地址與小孩生日，完成後系統即可產出推薦。

| 資料集 | 用途 |
| :---- | :---- |
| 各縣市**兒童遊戲場／共融遊戲場**清冊 | 法定登錄資料，品質最高；其「適用年齡」欄位可直接對應設施適齡層 |
| 各縣市**親子館／托育資源中心** | 室內主力，雨天備案 |
| 各縣市**公園設施資料** | 涵蓋面最廣 |
| **觀光資訊資料庫－景點** | 補足非公園類 |
| 圖書館／文化中心（選用） | 低放電室內選項 |

這些資料結構化、免費、有座標、無業配污染。部落格資料需 AI 抽取且品質參差，**不列入 Phase 1**。

匯入後依類別套用先驗值（§11.1），並批次計算基準車程。

### 10.2 即時資料

| 用途 | 來源 | 備註 |
| :---- | :---- | :---- |
| 天氣預報 | 中央氣象署開放資料平臺 | 鄉鎮天氣預報，逐 3 小時降雨機率與體感溫度；需免費授權碼 |
| 路徑規劃 | **Google Routes API** | 見 §10.3 |
| 停車位 | TDX 運輸資料流通服務平臺 | 僅用於即時剩餘車位（Google 不提供） |
| 連假判定 | 政府行政機關辦公日曆表 | 年度快取，無需即時查詢 |

### 10.3 Google Routes API 使用規範

**必須使用 Routes API。Directions API 與 Distance Matrix API 已被列為 Legacy，新專案不得採用。**

| 場景 | 設定 | 計費層級 |
| :---- | :---- | :---- |
| 匯入時算基準值 | 不含即時路況 | 較低階（每月 10,000 次免費） |
| 決策時精算 | 含即時路況 \+ 指定出發時刻 | 較高階（每月 5,000 次免費） |

矩陣查詢按「元素」計費（起點數 × 終點數）。以匯入 300 筆、每次推薦精算 8 個地點的去回程估算，週查 30 次的月用量約 2,000 元素，**在免費額度內**。

**成本控制規則**：

1. 即時路況僅用於硬過濾後存活的前 8 名，不得對全部地點呼叫  
2. 不走國道的地點可跳過即時查詢  
3. 同起訖點於短時間內的結果應快取  
4. **必須在雲端主控台設定配額上限**。預設無硬性上限，超額自動計費  
5. API 失敗時降級為係數估算，並將信心度標為低，**UI 須明示「路況資料暫時無法取得」，不得靜默使用低信心估值**

**車程顯示須標示來源與信心度**（例如「22 分（即時）」與「約 25 分（估算）」）。低信心估值不可偽裝成精確值。

**待確認事項**：Google Maps Platform 服務條款對路徑／ETA 結果的快取與長期儲存有限制。實作前須確認基準車程的長期儲存是否合規；若不合規，改為匯入時重算或以其他方式估算基準值。

## 12\. 開發階段

### Phase 1：可用

**目標：安裝後只輸入住家地址與小孩生日，即可在週末早晨收到可執行的建議。**

- 開放資料匯入器（縣市選擇 → 下載 → 正規化 → 套用類別先驗值）  
- 基準車程批次計算 \+ **雲端配額上限設定（動工第一件事）**  
- 小孩設定、家庭偏好初始三題  
- 天氣串接、連假判定  
- 推薦引擎三階段（含單元測試）  
- 推播訂閱與「加入主畫面」引導  
- 第一則推播（含「今天不要出門」路徑）與「去了／沒去」  
- 第二則推播與三次點擊回饋  
- 一次性情境輸入  
- 推播落地頁

**驗收標準一**：首次開啟，在僅輸入住家地址與小孩生日的情況下即可獲得三個合理推薦。**若仍需手動建檔才能使用，Phase 1 未完成。**

**驗收標準二**：連續四個週末，在**未主動開啟 App** 的前提下，僅憑推播內容即完成出遊決策。**若仍須開啟 App 才能決定，形態設計未成立。**

### Phase 2：累積

- 造訪紀錄的完整編輯（選填層）  
- 地點「建檔值 vs 實際紀錄」對照視圖  
- 歷史成效進入評分  
- 偏好學習與權重可視化  
- 探索槽與防同溫層機制  
- 候選 → 已驗證的晉升流程與標示  
- AI 用法 B、C、D  
- 停車位資料  
- 離線快取

### Phase 3：擴散

- 過夜規劃模式（住宿／包棟）  
- 分享單一推薦（觀察是否有他人主動想用）  
- 多使用者支援（此時才需要帳號系統）

### Phase 4：變現（僅在有真實他人使用者之後）

- 聯盟行銷連結  
- **不做展示廣告**（規模天花板太低，且注意力單價遠低於決策單價）  
- **不做業者付費上架**

**變現原則**：推薦排序與金錢完全隔離。聯盟連結只出現在使用者**已決定要去之後**的畫面。這條界線一旦破了，產品唯一的資產（誠實）就沒了。

## 13\. 給實作者的工作方式

### 13.1 起手順序

**第一步不是寫程式，是提出資料模型草案供討論。** 本文刻意不含 schema——請依 §6 的語彙與 §7 的流程設計，並說明取捨理由。確認後再往下。

之後建議：匯入器 → 天氣 → 推薦引擎（含測試）→ 推播 → 落地頁。

**不要一次生成全部 Phase 1。**

### 13.2 不可違反的約束

1. **推薦引擎為純函式**，不讀資料庫、不呼叫網路、不依賴 UI 狀態  
2. **AI 相關模組不得被推薦引擎引用**，建議以 lint 規則強制  
3. **AI 輸出須經驗證後才可進入推薦條件**，禁止直接傳入  
4. **適齡判斷在硬過濾階段**，不得移至評分扣分  
5. **小孩約束邏輯獨立於當日推薦引擎**，供未來過夜模式共用  
6. **除兩項回饋外，造訪紀錄所有欄位皆為選填**；表單不得將選填欄位設為必填  
7. **基準車程不得由使用者手動輸入**  
8. **第二則推播須在通知內完成回饋**，不得實作為導流通知  
9. **推播文案使用規則模板，不使用 AI 生成**，並與推薦理由共用同一組模板  
10. **門檻值、權重、係數集中管理**，便於長期調參

### 13.3 必要的測試案例

- 雨天：戶外全滅、偏好權重歸零、室內選項公平競爭  
- 午睡衝突：可用時間不足以完成往返時正確剔除  
- 適齡：無設施但可跑空間大的場館應存活；有設施但不適齡且無可跑空間者應剔除  
- 多小孩：取最低分而非平均  
- 連假：係數正確套用，回程獨立計算  
- 路況 API 失敗：降級估算、信心度標記、流程不中斷  
- 一次性情境：無法解析時流程照常完成；覆寫僅影響本次  
- 無存活地點：正確產出「今天不要出門」  
- 探索槽：不因長期未採納而消失  
- 歷史成效權重不超過 5%

### 13.4 風格

- 行動優先，以 375px 為基準  
- 所有 API 金鑰經伺服器端代理，不在前端出現  
- 地點資料須可匯出，避免被自身資料庫綁架
